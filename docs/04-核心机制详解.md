# 04 核心机制详解

本文档深入讲解项目中最关键的六个机制。这些是面试深挖的高频区域，也是理解系统行为的钥匙。

## 4.1 事件多路分发机制

### 4.1.1 问题背景

monitor 事件（工具调用、助手调度、结果）需要同时满足：

1. **实时性**：WebSocket 在线用户立即看到；
2. **可靠性**：断线用户重连后能补齐；
3. **跨进程**：worker 进程产生的事件要送到 API 进程的 WebSocket；
4. **可观测**：指标系统能统计。

### 4.1.2 分发策略

`ToolMonitor._emit()` 是唯一的事件出口，按当前进程角色分发：

```python
def _emit(self, event_type, message, data=None):
    payload = {"type": "monitor_event", "event": ..., "message": ..., 
               "data": ..., "timestamp": ...}
    thread_id = get_thread_context()
    
    # 1. 持久化（先落库再分发，回放数据不依赖推送成功）
    seq = self._persist_event(thread_id, event_type, message, payload["data"])
    if seq is not None:
        payload["seq"] = seq  # seq 写入 payload，前端据此去重
    
    # 2. 跨进程桥（worker 进程没有 WebSocket 管理器）
    if self.websocket_manager is None:
        self._publish_to_bridge(thread_id, payload)
    
    # 3. 进程内 WebSocket 推送（API 进程或单机模式）
    if self.websocket_manager:
        self._send_to_websocket(payload, thread_id, manager_loop)
    
    # 4. 日志 + 指标
    logger.info(...)
    if event_type == "tool_start":
        record_tool_call(...)
```

### 4.1.3 为什么先落库

如果先推送后落库，推送成功但落库失败时，回放数据缺失；先落库则保证“回放数据 ⊇ 实时数据”，前端按 seq 去重后不会重复。

### 4.1.4 seq 的作用

seq 是 thread_id 内单调递增的序号，写进 payload 后：

- 前端实时事件：`seq <= lastSeq` 的跳过（已回放过）；
- 前端回放：`after_seq=lastSeq` 拉取缺口；
- 两者交接点：回放的 max seq 成为实时推送的起点。

## 4.2 跨进程事件桥

### 4.2.1 问题背景

arq 模式下：

- WebSocket 连接在 API 进程（ConnectionManager 是进程内单例）；
- monitor 事件产生于 worker 进程（websocket_manager 为 None）。

### 4.2.2 架构

```
worker 进程                          API 进程
─────────────                        ─────────
monitor._emit()                      
  → websocket_manager is None        
  → RedisBridge.publish(thread_id)   
                          ─────────►  subscriber_loop()
                          Redis        → handler(thread_id, payload)
                          Pub/Sub      → ConnectionManager.send_to_thread()
                                         → WebSocket.send_json()
```

### 4.2.3 动态订阅

```python
async def subscriber_loop(self, thread_ids_provider, handler):
    pubsub = self._subscriber.pubsub()
    subscribed = set()
    while True:
        wanted = set(thread_ids_provider())  # 当前 WS 连接注册表
        # 订阅新增的
        for thread_id in wanted - subscribed:
            await pubsub.subscribe(f"{CHANNEL_PREFIX}{thread_id}")
            subscribed.add(thread_id)
        # 退订消失的
        for thread_id in subscribed - wanted:
            await pubsub.unsubscribe(...)
            subscribed.discard(thread_id)
        
        if not subscribed:
            await asyncio.sleep(0.5)  # 零订阅不能读消息（坑 8）
            continue
        
        message = await pubsub.get_message(timeout=1.0)
        # ...转发
```

**为什么动态订阅**：thread_id 每次任务都不同，不可能预先订阅所有频道；连接断开后及时退订避免资源泄漏。

### 4.2.4 可靠性设计

Pub/Sub 是“即发即忘”——发布时没有订阅者，消息直接丢弃。这没问题，因为：

- 事件已落库（EventStore），回放接口可补齐；
- 实时推送只是“锦上添花”，丢了不影响任务执行；
- 发布失败只记日志，不阻断任务。

## 4.3 协作式取消

### 4.3.1 问题背景

memory 模式下取消很简单：`asyncio.Task.cancel()` 注入 CancelledError。但 arq 模式下任务在另一个进程，API 进程无法取消它的 asyncio 任务。

### 4.3.2 协作式方案

```
取消接口                           worker 进程
────────                           ───────────
1. 校验归属
2. ArqTaskQueue.cancel()
   - 队列中未执行 → job.abort() → 真正中止
   - 运行中 → 返回 "cancelling"
3. TaskStore.set_status(cancelled)  ← 置位取消标记
4. 返回 {status: cancelling}
                                  5. 流式循环中定期检查：
                                     if chunk_count % 5 == 0 and _is_cancelled():
                                         break  ← 主动收尾
                                  6. 检测到取消 → 补发 task_cancelled 事件
```

### 4.3.3 检查频率

```python
_CANCEL_CHECK_INTERVAL = 5  # 每 5 个流式片段检查一次

chunk_count += 1
if chunk_count % _CANCEL_CHECK_INTERVAL == 0 and _is_cancelled(session_id):
    break
```

astream 的每个 chunk 大致对应一个节点执行，5 个片段约一次工具调用周期——取消响应延迟在可接受范围（秒级），且检查本身只是一次 SQLite 查询。

### 4.3.4 两种模式的统一

memory 模式的取消也走同一路径（置位 + 检查），保证行为一致：

- memory：`MemoryTaskQueue.cancel()` 直接取消 asyncio 任务（CancelledError 路径）；
- arq：置位 + 协作式收尾；
- 两者最终都调用 `task_store.set_status(cancelled)` 和 `monitor.report_task_cancelled()`。

## 4.4 断线回放与去重

### 4.4.1 完整流程

```
正常状态：
  worker → 事件(seq=1,2,3...) → WS 推送 → 前端 events=[1,2,3], lastSeq=3

断线（网络波动）：
  worker → 事件(seq=4,5) → 推送失败（无连接）→ 仅落库

重连：
  前端 WS 重连成功
  → GET /api/task/{id}/events?after_seq=3
  → 服务端返回 [{seq:4},{seq:5}]
  → 前端合并 events=[1,2,3,4,5], lastSeq=5
  → 实时推送恢复：seq=6 的事件正常追加（6 > 5）
```

### 4.4.2 去重的三种边界

1. **回放内部**：服务端 `seq > after_seq` 过滤；
2. **回放与实时交接**：实时事件 `seq <= lastSeq` 跳过；
3. **新会话**：thread 切换时 lastSeq 重置为 0（从头开始）。

### 4.4.3 为什么不用消息 ID 去重

消息 ID（UUID）去重需要前端维护已见 ID 集合（内存增长）；seq 是单调整数，一个变量即可判断“是否已见”。

## 4.5 检查点选型

### 4.5.1 三种实现对比

| 实现 | 异步支持 | 持久化 | 多进程共享 | 适用场景 |
| --- | --- | --- | --- | --- |
| InMemorySaver | 是 | 否 | 否 | 调试 |
| AsyncSqliteSaver | 是 | 是（文件） | 是（WAL） | 单机/开发 |
| AsyncPostgresSaver | 是 | 是（服务） | 是（原生） | 生产多实例 |

### 4.5.2 为什么必须异步

LangGraph 的 astream 执行路径：

```python
async for chunk in agent.astream(input, config):
    ...
```

astream 内部对每个节点执行后调用 `checkpointer.aput(...)`。同步的 SqliteSaver 只有 `put()`，没有 `aput()`——调用即报错。

### 4.5.3 惰性异步组装

```python
_main_agent = None
_agent_build_lock = asyncio.Lock()

async def get_main_agent():
    global _main_agent
    if _main_agent is not None:
        return _main_agent
    async with _agent_build_lock:  # 防并发重复构建
        if _main_agent is None:
            _main_agent = create_deep_agent(
                ...,
                checkpointer=await get_checkpointer(),  # 需要事件循环
            )
    return _main_agent
```

**为什么不能模块级组装**：`AsyncSqliteSaver` 的创建需要 `await aiosqlite.connect()`，模块导入时没有运行中的事件循环。

### 4.5.4 PostgreSQL 上下文管理器

```python
_checkpointer_cm = AsyncPostgresSaver.from_conn_string(dsn)
saver = await _checkpointer_cm.__aenter__()
await saver.setup()
# ...停机时
await _checkpointer_cm.__aexit__(None, None, None)
```

from_conn_string 返回异步上下文管理器，句柄保留在模块级，停机时正常退出关闭连接池。

## 4.6 评测三层判定

### 4.6.1 为什么需要三层

| 层 | 能力 | 成本 | 覆盖的问题 |
| --- | --- | --- | --- |
| 确定性检查 | 关键词命中/禁用语 | 零 | “答案里有没有关键信息” |
| 链路检查 | 期望工具是否被调用 | 零 | “工具真的被走到了吗” |
| LLM 评审 | 三维 rubric 打分 | 一次调用 | “回答质量好不好” |

纯规则无法判断质量（完整性、有据性），纯 LLM 成本高且不稳定。三层组合：零成本层每次 CI 跑，LLM 层按需触发。

### 4.6.2 判定逻辑

```python
passed = (
    deterministic["passed"]      # 关键词 + 禁用语
    and event_check["passed"]    # 期望事件 + 期望工具（全部命中）
    and not judge_error          # 评审本身没出错
    and weighted >= threshold    # 加权分 ≥ 0.6
)
```

### 4.6.3 执行过程复用

评测执行器复用主链路 `run_deep_agent`，执行事件天然落库到 EventStore——跑完按 thread_id 读回即可，无需额外埋点：

```python
async def run(query, seed_files=None):
    thread_id = f"eval_{uuid.uuid4().hex[:10]}"
    set_thread_context(thread_id)
    # 预置种子文件（文件读取类用例）
    if seed_files:
        # 复制到 updated/session_{thread_id}/
        ...
    await run_deep_agent(query, thread_id, user_id=None)
    events = get_event_store().list(thread_id)
    answer = extract_task_result(events)
    return answer, events
```
