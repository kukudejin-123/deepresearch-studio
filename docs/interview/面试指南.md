# 第二部分：高频问题与答题要点

> 24 个高频问题按主题分组。每题给的是**思路骨架**，不是背诵稿——用自己的话讲出来。

## 一、项目整体类

### Q1：介绍一下这个项目

**结构**：一句话定位 → 核心场景举例 → 技术架构 → 我的工作（参考第一部分的电梯陈述）。30 秒内让面试官理解“这是什么、难在哪、你做了什么”。

### Q2：为什么做这个项目？解决了什么问题？

- 起点：原版开源项目是教学骨架，README 自己声明了六项能力边界（无认证、无队列、无持久化、无测试、无评测、无部署）；
- 我的工作就是把这些边界补齐，验证“从 demo 到生产”需要什么；
- 深层动机：Agent 应用的工程化是行业痛点——模型效果之外，安全、可靠、可度量同样决定成败。

### Q3：项目基于开源项目，你的贡献是什么？

**主动承认，不回避**：

- 原项目提供：多智能体骨架、9 个工具、前后端闭环；
- 我新增：15 个模块（auth/queue/events/eval/worker/metrics 等）、172 个新测试、Docker 与 CI；
- 我修复：13 个真实缺陷（其中 4 个是原版就存在的：无认证、路径穿越、越权返回 200、隐藏文件绕过）；
- 面试官可以 clone 两个仓库 diff，每一行改动我都讲得清。

### Q4：项目有什么不足？

**主动说，显成熟**：

- 没有真实用户流量，生产验证靠工程链路（分布式端到端、CI、评测）；
- 角色权限是粗粒度模型（本人 or 拒绝），没有 RBAC；
- 运行中任务取消即终止，没有断点续跑（检查点具备恢复条件但 resume 未实现）；
- 多 API 实例部署时限流与 WebSocket 连接表还是进程内实现，需要换 Redis。

## 二、多智能体类

### Q5：为什么用一主三从架构，不用单智能体？

- 单智能体工具超过 5-6 个时，模型选择准确率显著下降；
- 专家分工让每个子智能体的提示词可以针对领域优化（数据库助手强调“先列表再预览再查询”的步骤）；
- 上下文隔离：子智能体的工具返回不会塞满主智能体的上下文。

### Q6：主智能体怎么决定调用哪个助手？

- DeepAgents 内部把子智能体封装为名为 `task` 的工具，主智能体根据每个助手的 `description` 路由；
- description 设计三原则：明确职责边界、排除法（不是什么）、举例（具体文档类型）；
- 提示词里还有兜底约束：“如果边界并不明确，则全部使用”。

### Q7：怎么防止模型编造内容（幻觉）？

**四层防线**：

1. 提示词约束：“必须先调用子智能体获取信息，绝不允许在获取信息之前调用文件生成工具”；
2. 禁止占位符：“严禁使用'等待子任务完成'之类的占位符内容生成文件”；
3. 分步执行：“先搜索再生成，分两步进行，不要在同一个 Tool Call 列表中同时做”；
4. 评测兜底：groundedness 维度专门评“结论是否有检索来源支撑”，回归对比能发现质量退化。

### Q8：子智能体之间能互相调用吗？

本项目不支持（DeepAgents 的字典式子智能体是扁平结构）。examples 里有嵌套示例，但“一主三从”已覆盖需求，嵌套会增加路由复杂度且难以调试。未来如需嵌套，可用 CompiledSubAgent 包装 LangGraph 子图实现。

### Q9：工具返回错误怎么处理？

- 工具内部捕获异常，返回中文错误提示字符串，**不向模型抛异常**；
- 原因：异常会中断整个 Agent 执行链；错误提示让模型可以自我纠正（如换表名重试）；
- 安全类拒绝（SQL 注入、路径穿越）也走同一路径——返回拒绝原因，模型看到后调整行为。

## 三、安全类

### Q10：JWT 和 Session 的区别？为什么选 JWT？

- Session：服务端存储会话状态，客户端持 session_id；有状态；
- JWT：无状态，token 自带用户身份（签名防篡改）；
- 选择原因：用户量小、不需要服务端主动失效；无状态让 API 层无依赖；
- 取舍：过期前无法服务端失效——缓解：校验时查用户是否存在（删号即失效）。

### Q11：越权访问怎么防护？为什么返回 404 不是 403？

- 所有资源接口校验归属：`task.user_id != current_user.id → 404`；
- 404 不暴露资源存在性（403 等于告诉攻击者“资源存在但不属于你”）；
- 文件路径用 `resolve()` + `is_relative_to()` 双重校验（防 `..` 穿越）。

### Q12：SQL 注入怎么防？模型生成的 SQL 不可信吧？

- 完全正确——模型生成的 SQL 默认不可信，工具层硬校验（sql_guard.py）；
- 五道关卡：长度限制 → 剥注释 → 首关键字白名单（SELECT/SHOW/WITH/EXPLAIN）→ 多语句检测 → 关键字黑名单（词边界匹配）；
- 表名单独过白名单（`get_table_data` 的拼接注入面）；
- 为什么先剥注释：`SELECT 1 -- ; DROP TABLE x` 实际只执行 SELECT 1，但需要识别这种异常模式。

### Q13：上传文件怎么防恶意文件？

- 三层：扩展名白名单 → 流式大小校验（超限立即中断删半成品）→ 文件名清洗（只取 basename、去控制字符、拒绝隐藏文件）；
- 修过的坑：`strip(".")` 会连 `.env` 前导点一起剥掉导致隐藏文件绕过，改 `rstrip(".")`；
- 未做：文件内容审核（病毒扫描）——需要外部安全服务，已列入能力边界。

### Q14：限流怎么实现的？分布式下呢？

- 滑动窗口（内存 deque）：任务按用户 10 次/分钟，登录按 IP+用户名 5 次/分钟；
- 单用户并发上限 2（计数来自共享 TaskStore，两种队列模式都生效）；
- 局限：进程内实现，多 API 实例各计数各的——生产需换 Redis 共享计数。

## 四、分布式与架构类

### Q15：为什么用 arq 不用 Celery？

- Celery 是同步设计（进程/线程模型），在 FastAPI 异步生态中需要额外适配（事件循环冲突）；
- arq 原生 async，与 astream 完全兼容；
- 且抽象了 TaskQueue 协议，未来可替换（memory → arq → 任何实现）。

### Q16：arq 模式下任务在 worker 执行，WebSocket 在 API 进程，事件怎么推？

**事件桥**（详见第三部分技术深挖）：

- worker 的 monitor 事件 → Redis Pub/Sub 发布（频道 `deepresearch:events:{thread_id}`）；
- API 进程订阅循环动态订阅活跃 thread（订阅范围 = WebSocket 连接注册表）；
- 可靠性：事件同时落库（EventStore），Pub/Sub 丢消息不影响回放；
- 修过的坑：零订阅时 get_message 会抛异常杀死订阅循环——加空订阅跳过。

### Q17：服务重启后运行中的任务怎么办？

- memory 模式：任务丢失（asyncio 任务随进程消亡），状态已落库（running 僵死）可查询；
- arq 模式：已入队未执行的任务不丢（Redis 持久化队列），重启后继续消费；
- 断点恢复：检查点已具备条件（LangGraph checkpoint），但 resume 未实现——已列入规划。

### Q18：断线重连后执行过程怎么补齐？

- 事件全量落库，每条带 thread_id 内单调递增的 seq；
- 前端记录 lastSeq，重连后调 `/api/task/{id}/events?after_seq={lastSeq}` 拉缺口；
- 实时事件与回放事件按 seq 去重（`seq <= lastSeq` 跳过）；
- 为什么用 seq 不用 UUID：单调整数一个变量判断“是否已见”。

### Q19：取消任务怎么实现的？跨进程怎么取消？

**协作式取消**（详见第三部分技术深挖）：

- 无法跨进程强杀 asyncio 任务 → 协作式：取消接口把状态置为 cancelled，worker 在流式循环中每 5 个 chunk 检查一次，检测到即 break 收尾；
- 队列中未执行的任务：arq 的 job.abort() 真正中止；
- 修过的坑：abort 默认无限等待 worker 确认（timeout=None），没有 worker 时取消接口永久挂死。

## 五、存储与数据类

### Q20：检查点为什么用 SQLite？为什么必须异步实现？

- SQLite：单文件、支持 SQL 查询（按 thread_id 检索）、部署简单；生产多实例切 PostgreSQL；
- 异步：astream 只调用检查点的异步接口（aput/aget），同步 SqliteSaver 没有这些方法，调用直接报错；
- 主智能体因此改为惰性异步组装（首次任务时创建，带并发锁）。

### Q21：FAISS 中文路径问题是什么？

- 现象：中文集合名建库时 `faiss.write_index` 报 "could not open for writing"；
- 根因：FAISS 的 C++ 写入层走窄字符文件 IO，Windows 上非 ASCII 路径直接失败；
- 修复：改用 `serialize_index` + Python 写盘；集合目录用 ASCII slug，中文名存 meta.json。

### Q22：多进程写 SQLite 不会锁吗？

- WAL 模式：读写不互斥，多进程可并发；
- busy_timeout=10s：瞬时写锁等待而非报错；
- 任务写入频率低（每任务几次状态变更），冲突概率极低；
- 生产多 worker 可切 PostgreSQL（检查点已支持）。

## 六、质量与测试类

### Q23：怎么保证 Agent 的输出质量？

**评测体系**（详见项目文档 06）：

- 三层判定：确定性检查（关键词/禁用语，零成本）+ 链路检查（期望工具是否被走到）+ LLM 评审（correctness/completeness/groundedness 三维）；
- 回归对比：跑两次评测对比，分数下降超阈值或由通过转失败即判定回归；
- CI 每周自动跑，报告存 artifact；
- 改提示词/工具后跑一次就知道影响——这是 Agent 工程的核心痛点。

### Q24：测试怎么写的？模型输出不确定怎么测？

- 模型相关：不测输出内容（非确定性），测行为链路（工具是否被调用、状态是否正确流转）；
- 外部依赖全 mock：FakeEmbeddings（确定性向量）、MySQL 池 mock、Agent 执行器 mock；
- 指标测试用增量断言（prometheus 全局对象跨测试共享）；
- 真实质量由评测体系覆盖（LLM-as-judge），测试覆盖工程正确性。

# 第三部分：技术深挖（原理与追问链）

> 面试官往下挖底层原理时的应对。每个主题：机制原理 → 本项目实现 → 可能的追问。

## 一、LangGraph 检查点机制

**原理**：检查点是图执行到某一步的完整状态快照（messages、channel_values、channel_versions）。每次节点执行后写入存储（按 thread_id 组织），恢复时从最新检查点读取继续。

**同步 vs 异步**：`astream` 内部调用 `checkpointer.aput(...)`——只调用异步接口，不会回退到同步方法。同步的 SqliteSaver 没有 `aput()`，调用即报错。

**追问链**：

- **Q：检查点存的是什么？全量还是增量？** A：全量快照。LangGraph 用 channel_versions 做增量追踪，但存储层是全量的——简单可靠。
- **Q：thread_id 相同的多次执行会怎样？** A：共享执行上下文——第二次执行 messages 接着第一次的（多轮对话的原理）。所以每个任务用独立 thread_id，避免任务间上下文污染。
- **Q：PostgreSQL 和 SQLite 检查点的区别？** A：接口完全一致（都实现 BaseCheckpointSaver）。区别在存储层：SQLite 单文件（WAL 支持多进程），PostgreSQL 网络服务（原生多实例并发）。生产多 worker 必须 PostgreSQL——SQLite 文件多机无法共享。

## 二、Redis Pub/Sub 与消息可靠性

**原理**：广播模型——发布者发消息，所有订阅者收到。**没有持久化、没有 ACK、没有重试**——发布时无订阅者，消息直接丢弃。

**为什么敢用**：事件同时落库（EventStore）。实时推送是“锦上添花”，可靠性由 SQLite 保证（断线回放补齐），发布失败只记日志不阻断任务。

**追问链**：

- **Q：Pub/Sub 丢消息怎么办？** A：设计上接受丢失——回放接口保证最终一致。要求“一条不丢”需换 Redis Stream（有 ACK 和消费者组），但复杂度上升。本项目事件是“过程展示”性质，允许丢失。
- **Q：动态订阅怎么做的？** A：订阅循环每轮从 WebSocket 连接注册表取活跃 thread_id，与已订阅集合做差集：新增 subscribe，消失 unsubscribe。零订阅时跳过 get_message（redis-py 在无订阅状态下调用会抛 "pubsub connection not set"——修过的坑）。
- **Q：为什么不用 Redis Stream？** A：Stream 的消费者组语义是为“任务不丢”设计的。事件推送不需要——丢了就回放。用 Stream 属于过度设计。

## 三、arq 任务队列

**原理**：asyncio 原生任务队列。生产者 `enqueue_job` 写入 Redis 有序集合；worker 轮询取出在事件循环中执行；任务状态 queued → running → complete/failed，结果存 Redis（带 TTL）。

**关键 API 与坑**：

```python
job = await pool.enqueue_job("run_agent_task", query, thread_id, user_id, _job_id=thread_id)
await job.abort(timeout=2.0)  # 必须显式超时！默认 None 无限等待 worker 确认
```

**追问链**：

- **Q：任务结果存哪里？** A：Redis（带 TTL）。本项目的任务结果以 TaskStore（SQLite）为准，arq 结果仅作补充。
- **Q：worker 崩溃了任务怎么办？** A：arq 有 in-progress 集合：worker 崩溃后重启时检测到会重新入队。本项目 max_tries=2（失败重试一次）。
- **Q：重试会不会重复执行副作用？** A：设计为幂等友好：任务状态覆盖写、事件 append-only（seq 单调不重复）、产物文件按 session_id 覆盖。重试不产生脏数据。

## 四、JWT 认证

**原理**：JWT = Base64(Header).Base64(Payload).Signature。服务端验签即可信任 Payload（无需查库），但**用户是否存在仍需查库**（防删号后旧 token 有效）。

**本项目的取舍**：密钥从环境变量读（默认值开发用，启动打警告）；有效期默认 24h；无 refresh token；query 参数传 token 的固有风险（进浏览器历史/日志）用短有效期缓解。

**追问链**：

- **Q：JWT 能撤销吗？** A：无状态 JWT 本身不能。撤销需要服务端黑名单（Redis）或短效 token + refresh。本项目用“校验时查用户存在”做弱撤销。
- **Q：HS256 和 RS256？** A：HS256 对称（单体服务够用）；RS256 非对称（私钥签发、公钥验证，适合微服务）。
- **Q：token 存 localStorage 安全吗？** A：有 XSS 风险。更安全是 httpOnly Cookie（但 CSRF 防护复杂）。本项目是内部工具，XSS 面小，localStorage + 严格 CSP 是合理取舍。

## 五、FAISS 向量检索

**原理**：向量存为连续内存数组，检索时计算查询向量与库内向量的距离。IndexFlatL2 暴力计算 L2 距离（精确，O(n)）；IVF 等索引聚类分桶（近似，O(√n) 有精度损失）。

**序列化与坑**：

```python
# 错误（C++ 层文件 IO，中文路径失败）
faiss.write_index(index, "中文路径/index.faiss")

# 正确（Python 层字节 IO）
raw = faiss.serialize_index(index)
path.write_bytes(raw.tobytes())
```

**追问链**：

- **Q：L2 距离和余弦相似度？** A：L2 受向量模长影响；余弦是方向相似。OpenAI/百炼的 embedding 通常已归一化，两者等价（IndexFlatIP 内积 = 归一化后的余弦）。
- **Q：分片策略怎么定的？** A：500 字符、重叠 80。中文研报段落通常 200-800 字符，500 覆盖一个完整论点；重叠 80 防论点被切断。分隔符优先级：段落 → 换行 → 句号 → 分号 → 逗号。
- **Q：百万级向量怎么办？** A：换 IVF 索引或专用向量数据库（Milvus/Qdrant）。本项目数据量远未触及，FAISS 单文件部署简单是首要考虑。

## 六、Prometheus 指标

**原理**：拉模式——定期抓取 `/metrics`，存时序数据库。四种类型：Counter（只增）、Gauge（可增可减）、Histogram（分布，服务端分桶）、Summary（分位数，客户端计算）。

**标签基数控制**：HTTP 指标的 path 用路由模板（`/api/task/{thread_id}`）而不是具体 ID——否则标签基数爆炸（每个 thread_id 一个时间序列）。

**追问链**：

- **Q：Counter 和 Gauge？** A：Counter 单调递增（重启归零，用 rate() 算速率）；Gauge 瞬时值（直接读）。任务量用 Counter，活跃数用 Gauge。
- **Q：Histogram 和 Summary？** A：Histogram 服务端分桶（可聚合多实例）；Summary 客户端分位数（准确但不可聚合）。多实例必须 Histogram。
- **Q：多进程指标怎么聚合？** A：每进程暴露自己的 /metrics，Prometheus 分别抓取（加 instance 标签）。arq 模式下 worker 的结局指标在 worker 进程——需要 worker 也暴露端点或 Pushgateway。

## 七、LLM-as-judge 评测

**原理**：用强模型评审输出。关键设计：结构化输出（强制 JSON，失败重试）、temperature=0（确定性）、rubric 明确、只依据给定材料。

**三维设计**：correctness（防编造）、completeness（防偷懒）、groundedness（防幻觉）。

**追问链**：

- **Q：LLM 评审可靠吗？** A：有主观性（temperature=0 缓解但无法消除）。缓解：明确 rubric、只依据给定材料、宁严勿松。工程上更可靠的是“确定性检查 + LLM 评审”组合。
- **Q：为什么不用人工评估？** A：成本。22 用例人工评一次几小时，LLM 几分钟。人工用于校准（定期抽检一致性），不是每次跑。
- **Q：评审模型和被测模型一样会怎样？** A：同模型自评有偏袒风险。缓解：评审模型强于被测模型，或人工抽检校准。本项目默认一致（成本考虑），生产建议换更强模型。

# 第四部分：踩坑复盘（13 个真实缺陷）

> 每个坑按“现象 → 排查 → 根因 → 修复 → 反思”结构。**口头讲挑 3 个讲透**（推荐坑 1、4、7），其余说“都记录在项目文档里”。

## 坑 1：FAISS 中文路径写入失败

**现象**：中文集合名（如“电商行业”）构建向量库时，`faiss.write_index` 报 "could not open ... for writing: No such file or directory"——目录明明已创建。

**排查**：英文集合名正常，中文名必现。进一步发现：项目路径含中文时，**即使集合名是英文也会失败**——问题在整条路径的任何非 ASCII 字符。

**根因**：FAISS 的 C++ 写入层走窄字符（char*）文件 IO。Windows 上非 ASCII 路径传给 C++ 层时编码丢失。Python 层的 `open()` 没问题（宽字符 API），但 FAISS 内部没用。

**修复**：绕开 C++ 文件 IO——`faiss.serialize_index()` 得到字节数组，Python 写盘；读取用 `deserialize_index(np.frombuffer(...))`。集合目录改用 ASCII slug（名称片段 + SHA1 哈希），中文名存 meta.json。

**反思**：跨语言库（Python 包装 C++）的路径处理是经典坑。这个坑在中文 Windows 用户身上 100% 复现，英文环境完全正常——环境差异让问题极具隐蔽性。教训：涉及文件 IO 的第三方库，先用非 ASCII 路径测一遍。

## 坑 2：同步检查点不支持异步图

**现象**：把 `InMemorySaver` 换成 `SqliteSaver` 后，任务执行报 "The SqliteSaver does not support async methods"。

**排查**：查 LangGraph 源码：`astream` 内部对每个节点执行后调用 `checkpointer.aput(...)`。同步的 SqliteSaver 只有 `put()`，没有 `aput()`。

**根因**：LangGraph 的异步执行路径只调用检查点的异步接口，不会回退到同步方法——异步图中混用同步 IO 会阻塞事件循环，这是 API 设计使然。

**修复**：改用 `AsyncSqliteSaver`（aiosqlite 驱动）。连带问题：创建需要 `await aiosqlite.connect()`，模块导入时没有事件循环——主智能体改为**惰性异步组装**（首次任务时创建，带 asyncio.Lock 防并发重复构建）。

**反思**：异步生态里“同步实现”不是降级选项而是不兼容。附带产出的惰性组装模式（锁 + 双重检查）也是并发编程的标准实践。

## 坑 3：arq func() 装饰器误用

**现象**：worker 启动崩溃：`TypeError: func() missing 1 required positional argument: 'coroutine'`。

**排查**：错误指向 `@func(name=..., timeout=...)` 装饰器。查 arq 源码：`func` 签名是 `func(coroutine, *, name=None, ...)`——第一个参数是**位置参数**。`@func(name=...)` 纯关键字写法把 coroutine 漏了。

**根因**：Python 装饰器的常见误用。`@decorator` 等价于 `func(被装饰函数)`，但 `@decorator(kwargs)` 等价于 `decorator(kwargs)(被装饰函数)`——arq 的 func 不支持前者。

**修复**：显式构造：`functions = [func(run_agent_task, name=..., timeout=1800, max_tries=2)]`。

**反思**：库的装饰器 API 要看签名再写。报错信息里的 "missing 1 required positional argument" 直接读，别猜。

## 坑 4：Job.abort() 无限等待挂死取消接口

**现象**：arq 模式下，取消接口永久不返回（测试脚本 60 秒超时被杀）。

**排查**：加日志发现卡在 `await job.abort()`。查 arq 源码：

```python
async def abort(self, *, timeout=None, poll_delay=0.5):
    ...
    await self.result(timeout=timeout, ...)  # timeout=None 无限等待！
```

**根因**：abort 的语义是“中止并等待结果确认”。timeout 默认 None——没有 worker 消费任务时，结果永远不来，等待永远无法完成。HTTP 请求被挂死。

**修复**：显式传超时 `job.abort(timeout=2.0)`。中止信号在等待前已写入 Redis，超时仅表示“没有 worker 确认”，不影响已排队任务被真正中止。

**反思**：第三方库的“等待确认”类 API 默认值往往是无限等待——这在库内部合理（worker 场景总会有人确认），但在 HTTP 请求上下文里是灾难。教训：任何 await 外部确认的调用，在请求处理路径上必须带超时。

## 坑 5：WebSocket 重复 accept

**现象**：带 token 连接 WebSocket 时报 "Expected ASGI message 'websocket.send' or 'websocket.close', but got 'websocket.accept'"。

**排查**：ASGI 协议规定 WebSocket 握手只能 accept 一次。搜代码发现两处：认证辅助函数里一次，`manager.connect()` 里又一次。

**根因**：职责划分不清——认证函数既做认证又做协议操作。

**修复**：认证函数只校验（失败时 close），成功时不 accept；accept 统一由 ConnectionManager 执行。

**反思**：协议操作（accept/close）应该集中在连接管理层，认证是前置检查。

## 坑 6：WebSocket 归属校验过严挡死正常流程

**现象**：端到端测试中，前端“先建 WebSocket 再提交任务”的正常流程被 403 拒绝。

**排查**：最初的安全设计是“任务必须存在且属于本人”。但前端的工作流是：客户端预生成 thread_id → 建立 WebSocket（此时任务还没提交）→ 提交任务。连接时 `task_store.get(thread_id)` 返回 None，被当作“不存在”拒绝。

**根因**：安全校验与业务流程冲突——把“预订阅”误判为“越权访问”。

**修复**：区分两种“任务不存在”：还没提交 → 允许连接（thread_id 是 UUID 且按用户本地存储，猜测他人 thread_id 可行性可忽略）；任务属于他人 → 拒绝（4404）。

**反思**：安全校验要考虑正常业务流程，不能只防攻击面。设计校验规则时，先把“合法用户的正常操作序列”列出来，逐条验证不会被误伤。

## 坑 7：Redis 订阅循环零订阅崩溃（最隐蔽的坑）

**现象**：arq 模式下事件完全不推送（但落库正常、任务执行正常）。API 日志里只有一行异常，之后一切如常。

**排查**：这个坑排查了很久——“不推送”本身不报错，所有接口都正常。最后在 API 启动日志里发现一行：

```
ERROR | app.events.bridge | Redis 订阅循环异常:
pubsub connection not set: did you forget to call subscribe() or psubscribe()?
```

**根因**：API 启动时还没有任何 WebSocket 连接，订阅循环第一轮 wanted 和 subscribed 都是空集——直接调用 `pubsub.get_message()`。redis-py 在“从未订阅过任何频道”的状态下调用会抛异常。异常被 `except Exception` 捕获后，**循环退出**——桥接静默死亡，且没有任何后续症状。

**修复**：零订阅时跳过读取：

```python
if not subscribed:
    await asyncio.sleep(0.5)
    continue
```

**反思**：这是整个项目最值得讲的坑——“一切正常但功能失效”的静默故障。三个教训：

1. 后台任务的异常处理不能只是“记日志”——要区分“可恢复”和“该退出”，订阅循环应该 continue 而不是退出；
2. 测试覆盖了“有连接时推送”，没覆盖“启动后首个连接建立前”的时间窗；
3. 端到端验证（真实起两个进程）才能发现这类问题，单元测试的 mock 环境掩盖了它。

## 坑 8：隐藏文件绕过上传检查

**现象**：`.env` 文件上传后落盘为 `env`（前导点被剥掉），隐藏文件检查失效。

**排查**：`sanitize_filename` 里 `name.strip(".")` 同时剥离首尾点号。`.env` → `env`，后续 `if name.startswith(".")` 永远不触发。

**根因**：`strip()` 不区分首尾。想剥尾部点号（Windows 不允许文件名以点结尾）却把首部也剥了。

**修复**：`rstrip(".")`（只剥尾部），前导点保留供下一步拒绝。

**反思**：字符串处理函数的“顺手”用法是安全漏洞的高发区。安全相关的字符串操作，每个字符的处理都要明确意图。

## 坑 9：越权访问返回 200

**现象**：用户 B 下载用户 A 的文件返回 HTTP 200，响应体是 `{"error": "拒绝访问"}`。

**排查**：原版文件接口用“200 + 错误 JSON”表示拒绝。浏览器收到 200 会当作成功处理（下载一个内容是错误 JSON 的文件），监控系统也统计为成功请求。

**根因**：HTTP 语义误用——错误状态必须用错误码表达。

**修复**：越权 → 403，不存在 → 404，用 HTTPException 抛出。

**反思**：REST API 的基本功。设计接口时先定错误码规范，再写实现；测试要断言状态码而不只是响应体。

## 坑 10：评测工具匹配失效（集合成员 vs 子串）

**现象**：所有用例的链路检查都失败，missing_tools 包含全部期望工具。

**排查**：`run_event_checks` 里 `expected.lower() not in {name.lower() for name in tool_names}` 是**集合成员判断**（要求完全相等）。工具名是“数据库表名查询工具：list_sql_tables”这样的长字符串，期望值“数据库”永远不相等。

**根因**：把“子串匹配”写成了“集合成员判断”。`in` 对 set 是成员判断，对 str 才是子串——一字之差，语义全变。

**修复**：`if not any(expected.lower() in name for name in normalized_tools)`。

**反思**：Python 的 `in` 运算符多态是经典陷阱。写匹配逻辑时先问“我要的是相等还是包含”，再用对应数据结构。

## 坑 11：空权重导致加权分恒 0

**现象**：mock 评审返回全 0.8 分，但所有用例的加权分算出 0.0，全部判失败。

**排查**：`compute_weighted_score(scores, {})` 中权重为空 → 加权和是 0（没有维度参与）→ 除法得 0。`or 1.0` 只防了除零，没防“分子为 0”。

**修复**：空权重时退化为三维算术平均。

**反思**：防御性编程要覆盖“空输入”而不只是“零值”。数学函数先定义空输入语义（这里是“无偏好 = 等权”）。

## 坑 12：Embedding 批量结果静默过滤

**现象**：代码审查发现（非运行时）：`return [v for v in results if v is not None]`。

**排查**：如果某个文本的向量化失败（results 中对应位置是 None），过滤后返回的向量数量少于输入文本数量——**返回向量与输入文本错位**。FAISS 拿到错误的分片向量，且不报错，极难排查。

**修复**：严格校验，任何缺失直接抛错（`_finalize()`）。

**反思**：“静默降级”比“响亮失败”危险得多。批处理接口必须保证“输入输出一一对应”，宁可以整个批次失败，不能返回错位的数据。

## 坑 13：同秒提交排序不稳定

**现象**：测试中连续保存两次运行，`list_runs()` 返回顺序随机。

**排查**：`ORDER BY created_at DESC`——SQLite 的 `datetime('now')` 精度到秒，同一秒内的两条记录排序未定义。

**修复**：补 `rowid DESC` 次级排序（rowid 是自增主键，同秒内按插入顺序）。任务列表（TaskStore）同样问题一并修复。

**反思**：时间列做排序键时，要么提高精度（毫秒），要么加自增 ID 兜底。

## 讲坑的技巧

1. **挑 3 个讲透**：坑 1（中文路径）、坑 4（无限等待）、坑 7（静默故障）最有技术含量，每个讲 5 分钟；
2. **按结构讲**：现象（怎么发现的）→ 排查（怎么定位的）→ 根因（为什么会这样）→ 修复（怎么解决的）→ 反思（学到了什么）；
3. **反思是加分项**：面试官听过的“坑”太多了，但“从这个坑学到的方法论”很少见——比如坑 7 的“后台任务异常处理要区分可恢复/该退出”；
