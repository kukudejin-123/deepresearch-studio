# 04 踩坑复盘

本文档记录 13 个真实缺陷的完整排查过程。**这是面试中最有价值的素材**——每个坑都能展开讲五分钟，证明你是真写过代码、真排查过问题的人。讲的时候按“现象 → 排查 → 根因 → 修复 → 反思”结构。

## 坑 1：FAISS 中文路径写入失败

**现象**：用中文集合名（如“电商行业”）构建向量库时，`faiss.write_index` 报错：

```
RuntimeError: Error in faiss::FileIOWriter::FileIOWriter(const char *):
could not open ...\电商行业\index.faiss for writing: No such file or directory
```

**排查**：目录明明已创建（mkdir 成功），文件却“不存在”。测试发现：英文集合名正常，中文名必现。进一步测试：项目路径含中文（“deepsearch-agents 项目”目录）时，**即使集合名是英文也会失败**——问题在整条路径的任何非 ASCII 字符。

**根因**：FAISS 的 C++ 写入层（`faiss.write_index`）走窄字符（char*）文件 IO。Windows 上非 ASCII 路径传给 C++ 层时编码丢失，文件打开失败。Python 层的 `open()` 没问题（宽字符 API），但 FAISS 内部没用。

**修复**：绕开 C++ 文件 IO——用 `faiss.serialize_index()` 得到 numpy 字节数组，Python 写盘；读取用 `faiss.deserialize_index(np.frombuffer(...))`。集合目录同时改用 ASCII slug（名称片段 + SHA1 哈希），中文展示名存 meta.json。

**反思**：跨语言库（Python 包装 C++）的路径处理是经典坑。教训：涉及文件 IO 的第三方库，先用非 ASCII 路径测一遍。这个坑在中文 Windows 用户身上 100% 复现，英文环境完全正常——环境差异让问题极具隐蔽性。

## 坑 2：同步检查点不支持异步图

**现象**：把 `InMemorySaver` 换成 `SqliteSaver` 后，任务执行报错：

```
The SqliteSaver does not support async methods.
Consider using AsyncSqliteSaver instead.
```

**排查**：错误信息很明确，但为什么“同步的不能用”？查 LangGraph 源码：`astream` 内部对每个节点执行后调用 `checkpointer.aput(...)`。同步的 SqliteSaver 只有 `put()`，没有 `aput()`——调用即 AttributeError，被 LangGraph 包装成上述提示。

**根因**：LangGraph 的异步执行路径只调用检查点的异步接口，不会回退到同步方法。这是 API 设计使然（异步图中混用同步 IO 会阻塞事件循环）。

**修复**：改用 `AsyncSqliteSaver`（aiosqlite 驱动）。连带问题：`AsyncSqliteSaver` 的创建需要 `await aiosqlite.connect()`，模块导入时没有事件循环——主智能体改为**惰性异步组装**（首次任务时创建，带 asyncio.Lock 防并发重复构建）。

**反思**：异步生态里“同步实现”不是降级选项而是不兼容。教训：选型时确认接口的异步支持，不要想当然。附带产出的惰性组装模式（锁 + 双重检查）也是并发编程的标准实践。

## 坑 3：arq func() 装饰器误用

**现象**：worker 启动直接崩溃：

```
TypeError: func() missing 1 required positional argument: 'coroutine'
```

**排查**：错误指向 `@func(name=..., timeout=..., max_tries=...)` 装饰器。查 arq 源码：`func` 的签名是 `func(coroutine, *, name=None, ...)`——第一个参数是**位置参数**。`@func(name=...)` 这种纯关键字装饰器写法把 coroutine 漏了。

**根因**：Python 装饰器的常见误用。`@decorator` 等价于 `func(被装饰函数)`，但 `@decorator(kwargs)` 等价于 `decorator(kwargs)(被装饰函数)`——arq 的 func 不支持前者。

**修复**：显式构造 Function 对象：

```python
functions = [
    func(run_agent_task, name="run_agent_task", timeout=1800, max_tries=2)
]
```

**反思**：库的装饰器 API 要看签名再写。这个坑 5 分钟就能修，但不知道的话会一直卡着——教训：报错信息里的 "missing 1 required positional argument" 直接读，别猜。

## 坑 4：Job.abort() 无限等待挂死取消接口

**现象**：arq 模式下，取消接口永久不返回（测试脚本 60 秒超时被杀）。

**排查**：在 `ArqTaskQueue.cancel()` 加日志，发现卡在 `await job.abort()`。查 arq 源码：

```python
async def abort(self, *, timeout=None, poll_delay=0.5):
    ...
    await self.result(timeout=timeout, poll_delay=poll_delay)  # timeout=None 无限等待！
```

**根因**：abort 的语义是“中止并等待结果确认”。timeout 默认 None——没有 worker 消费任务时，结果永远不来，等待永远无法完成。HTTP 请求被挂死。

**修复**：显式传超时 `job.abort(timeout=2.0)`。中止信号（zadd 到 abort_jobs_ss）在等待前已写入 Redis，超时仅表示“没有 worker 确认”，不影响已排队任务被真正中止。

**反思**：第三方库的“等待确认”类 API 默认值往往是无限等待——这在库内部合理（worker 场景总会有人确认），但在 HTTP 请求上下文里是灾难。教训：任何 await 外部确认的调用，在请求处理路径上必须带超时。

## 坑 5：WebSocket 重复 accept

**现象**：带 token 连接 WebSocket 时报：

```
RuntimeError: Expected ASGI message "websocket.send" or "websocket.close",
but got 'websocket.accept'
```

**排查**：ASGI 协议规定 WebSocket 握手只能 accept 一次。搜代码发现两处 accept：认证辅助函数 `_authenticate_websocket` 里调了一次，`manager.connect()` 里又调了一次。

**根因**：职责划分不清——认证函数既做认证又做协议操作。

**修复**：认证函数只校验（失败时 close），成功时不 accept；accept 统一由 ConnectionManager 执行。

**反思**：协议操作（accept/close）应该集中在连接管理层，认证是前置检查。教训：写 ASGI 中间逻辑时，先想清楚“谁负责协议状态机”。

## 坑 6：WebSocket 归属校验过严挡死正常流程

**现象**：端到端测试中，前端“先建 WebSocket 再提交任务”的流程被 403 拒绝。

**排查**：最初的安全设计是“任务必须存在且属于本人”。但前端的正常工作流是：客户端预生成 thread_id → 建立 WebSocket（此时任务还没提交）→ 提交任务。连接时 `task_store.get(thread_id)` 返回 None，被当作“不存在”拒绝。

**根因**：安全校验与业务流程冲突——把“预订阅”误判为“越权访问”。

**修复**：区分两种“任务不存在”：

- 任务不存在（还没提交）→ 允许连接（thread_id 是 UUID 且按用户本地存储，猜测他人 thread_id 可行性可忽略）；
- 任务存在但不属于本人 → 拒绝（4404）。

**反思**：安全校验要考虑正常业务流程，不能只防攻击面。教训：设计校验规则时，先把“合法用户的正常操作序列”列出来，逐条验证不会被误伤。

## 坑 7：Redis 订阅循环零订阅崩溃（最隐蔽的坑）

**现象**：arq 模式下事件完全不推送（但落库正常、任务执行正常）。API 日志里只有一行异常，之后一切如常。

**排查**：这个坑排查了很久——因为“不推送”本身不报错，所有接口都正常。最后在 API 启动日志里发现一行：

```
ERROR | app.events.bridge | Redis 订阅循环异常:
pubsub connection not set: did you forget to call subscribe() or psubscribe()?
```

**根因**：API 启动时还没有任何 WebSocket 连接，订阅循环第一轮 `wanted` 是空集，`subscribed` 也是空集——直接调用 `pubsub.get_message()`。redis-py 在“从未订阅过任何频道”的状态下调用 get_message 会抛异常。异常被 `except Exception as e: logger.exception(...)` 捕获后，**循环退出**——桥接静默死亡，且没有任何后续症状。

**修复**：零订阅时跳过读取：

```python
if not subscribed:
    await asyncio.sleep(0.5)
    continue
```

**反思**：这是整个项目最值得讲的坑——“一切正常但功能失效”的静默故障。三个教训：

1. 后台任务的异常处理不能只是“记日志”——要区分“可恢复”和“该退出”，订阅循环应该 continue 而不是退出；
2. 测试覆盖了“有连接时推送”，没覆盖“启动后首个连接建立前”的时间窗；
3. 端到端验证（真实起两个进程）才能发现这类问题，单元测试的 mock 环境掩盖了它。

## 坑 8：隐藏文件绕过上传检查

**现象**：测试发现 `.env` 文件上传后落盘为 `env`（前导点被剥掉），隐藏文件检查失效。

**排查**：`sanitize_filename` 里 `name.strip(".")` 同时剥离首尾点号。`.env` → `env`，后续 `if name.startswith(".")` 检查永远不触发。

**根因**：`strip()` 不区分首尾。想剥尾部点号（Windows 不允许文件名以点结尾）却把首部也剥了。

**修复**：`rstrip(".")`（只剥尾部），前导点保留供下一步拒绝。

**反思**：字符串处理函数的“顺手”用法是安全漏洞的高发区。教训：安全相关的字符串操作，每个字符的处理都要明确意图（这个点是“非法尾字符”还是“隐藏文件标记”）。

## 坑 9：越权访问返回 200

**现象**：端到端测试发现用户 B 下载用户 A 的文件返回 HTTP 200，响应体是 `{"error": "拒绝访问"}`。

**排查**：原版文件接口用“200 + 错误 JSON”表示拒绝。浏览器收到 200 会当作成功处理（下载一个内容是错误 JSON 的文件），监控系统也统计为成功请求。

**根因**：HTTP 语义误用——错误状态必须用错误码表达。

**修复**：越权 → 403，不存在 → 404，用 HTTPException 抛出。

**反思**：REST API 的基本功。教训：设计接口时先定错误码规范，再写实现；测试要断言状态码而不只是响应体。

## 坑 10：评测工具匹配失效（集合成员 vs 子串）

**现象**：所有用例的链路检查都失败，missing_tools 包含全部期望工具。

**排查**：`run_event_checks` 里：

```python
missing_tools = [
    expected for expected in case.expected_tools
    if expected.lower() not in {name.lower() for name in tool_names}  # 集合成员判断
]
```

工具名是“数据库表名查询工具：list_sql_tables”这样的长字符串，期望值“数据库”与它**完全不相等**——集合成员判断永远 False。

**根因**：把“子串匹配”写成了“集合成员判断”。`in` 对 set 是成员判断，对 str 才是子串——一字之差，语义全变。

**修复**：

```python
missing_tools = [
    expected for expected in case.expected_tools
    if not any(expected.lower() in name for name in normalized_tools)
]
```

**反思**：Python 的 `in` 运算符多态是经典陷阱。教训：写匹配逻辑时先问“我要的是相等还是包含”，再用对应数据结构；测试用例要覆盖“部分匹配”场景。

## 坑 11：空权重导致加权分恒 0

**现象**：mock 评审返回全 0.8 分，但所有用例的加权分算出 0.0，全部判失败。

**排查**：`compute_weighted_score(scores, {})`：

```python
total = sum(weights.values()) or 1.0  # {} → 0 → 1.0
weighted = sum(scores[d] * w for d, w in weights.items())  # {} → 0
return round(weighted / total, 3)  # 0 / 1.0 = 0.0
```

**根因**：空 weights 时加权和是 0（没有维度参与），除法得 0。`or 1.0` 只防了除零，没防“分子为 0”。

**修复**：空权重时退化为三维算术平均：

```python
effective = weights or {"correctness": 1, "completeness": 1, "groundedness": 1}
```

**反思**：防御性编程要覆盖“空输入”而不只是“零值”。教训：数学函数先定义空输入语义（这里是“无偏好 = 等权”）。

## 坑 12：Embedding 批量结果静默过滤

**现象**：代码审查发现（非运行时）：

```python
return [vector for vector in results if vector is not None]
```

**排查**：如果某个文本的向量化失败（results 中对应位置是 None），过滤后返回的向量数量少于输入文本数量——**返回向量与输入文本错位**。FAISS 拿到错误的分片向量，且不报错，极难排查。

**根因**：用“过滤”处理“缺失”，破坏了位置对应关系。

**修复**：严格校验，任何缺失直接抛错：

```python
def _finalize(results):
    vectors = []
    for vector in results:
        if vector is None:
            raise RuntimeError("Embedding 结果与输入文本数量不一致")
        vectors.append(vector)
    return vectors
```

**反思**：“静默降级”比“响亮失败”危险得多。教训：批处理接口必须保证“输入输出一一对应”，宁可以整个批次失败，不能返回错位的数据。

## 坑 13：同秒提交排序不稳定

**现象**：测试中连续保存两次运行，`list_runs()` 返回顺序随机。

**排查**：`ORDER BY created_at DESC`——SQLite 的 `datetime('now', 'localtime')` 精度到秒，同一秒内的两条记录排序未定义。

**根因**：时间戳精度不足以做排序键。

**修复**：补 `rowid DESC` 次级排序（rowid 是自增主键，同秒内按插入顺序）：

```sql
ORDER BY created_at DESC, rowid DESC
```

**反思**：任务列表（TaskStore）也有同样问题，一并修复。教训：时间列做排序键时，要么提高精度（毫秒），要么加自增 ID 兜底。

## 讲坑的技巧

1. **挑 3 个讲透**：坑 7（静默故障）、坑 4（无限等待）、坑 1（中文路径）最有技术含量，每个讲 5 分钟；
2. **按结构讲**：现象（怎么发现的）→ 排查（怎么定位的）→ 根因（为什么会这样）→ 修复（怎么解决的）→ 反思（学到了什么）；
3. **反思是加分项**：面试官听过的“坑”太多了，但“从这个坑学到的方法论”很少见——比如坑 7 的“后台任务异常处理要区分可恢复/该退出”；
4. **别贪多**：13 个坑列在文档里，口头讲 3 个就够，剩下的说“还有十几个都记录在项目文档里，面试后您可以看”。
