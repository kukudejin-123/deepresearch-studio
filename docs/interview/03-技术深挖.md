# 03 技术深挖

本文档覆盖面试中“底层原理”类追问。每个主题给出：机制原理 → 本项目实现 → 可能的追问链。

## 3.1 LangGraph 检查点机制

### 3.1.1 原理

LangGraph 把 Agent 执行建模为状态图（StateGraph）。检查点（Checkpoint）是图执行到某一步的完整状态快照：

```
messages: [...]        # 对话历史
channel_values: {...}  # 各通道的值
channel_versions: {...}# 版本向量（用于增量更新）
```

每次节点执行后，checkpointer 把新状态写入存储（按 thread_id 组织）。恢复执行时，从最新检查点读取状态继续。

### 3.1.2 同步 vs 异步

LangGraph 的执行接口：

- `invoke()` / `stream()`：同步，调用 checkpointer 的 `put()` / `get_tuple()`；
- `ainvoke()` / `astream()`：异步，调用 `aput()` / `aget_tuple()`。

**关键**：`astream` 不会回退到同步方法——同步的 SqliteSaver 在异步图中直接报 "does not support async methods"。

### 3.1.3 追问链

**Q：检查点存的是什么？messages 全量还是增量？**
A：全量快照（每次 put 写入当前完整状态）。LangGraph 用 channel_versions 做增量追踪，但存储层是全量的——简单可靠，状态图规模不大时完全够用。

**Q：thread_id 相同的多次执行会怎样？**
A：同一 thread_id 共享执行上下文——第二次执行时 messages 会接着第一次的（多轮对话的原理）。所以本项目每个任务用独立 thread_id（session_id），避免任务间上下文污染。

**Q：PostgreSQL 检查点和 SQLite 的区别？**
A：接口完全一致（都实现 BaseCheckpointSaver）。区别在存储层：SQLite 是单文件（WAL 支持多进程），PostgreSQL 是网络服务（原生多实例并发 + 连接池）。生产多 worker 必须 PostgreSQL——SQLite 文件在多机部署下无法共享。

## 3.2 Redis Pub/Sub 与消息可靠性

### 3.2.1 原理

Pub/Sub 是广播模型：发布者往频道发消息，所有订阅者收到。**没有持久化、没有 ACK、没有重试**——发布时无订阅者，消息直接丢弃。

### 3.2.2 为什么本项目敢用

因为事件同时落库（EventStore）：

- 实时推送是“锦上添花”（在线用户立即看到）；
- 可靠性由 SQLite 保证（断线回放补齐）；
- 发布失败只记日志，不阻断任务执行。

### 3.2.3 追问链

**Q：Pub/Sub 丢消息怎么办？**
A：设计上接受丢失——回放接口保证最终一致。如果业务要求“一条不丢”，需要换 Redis Stream（有 ACK 和消费者组）或消息队列（RabbitMQ/Kafka），但复杂度上升。本项目的事件是“过程展示”性质，允许丢失。

**Q：动态订阅怎么做的？**
A：订阅循环每轮从 WebSocket 连接注册表取活跃 thread_id 列表，与已订阅集合做差集：新增的 subscribe，消失的 unsubscribe。零订阅时跳过 get_message（redis-py 在无订阅状态下调用会抛 "pubsub connection not set"——这是修过的坑）。

**Q：为什么不用 Redis Stream？**
A：Stream 的消费者组语义（ACK、pending list）是为“任务不丢”设计的。事件推送不需要——丢了就回放。用 Stream 属于过度设计。

## 3.3 arq 任务队列

### 3.3.1 原理

arq 是 asyncio 原生的任务队列：

- 生产者：`pool.enqueue_job(func_name, *args, _job_id=...)` 把任务写入 Redis 有序集合；
- 消费者（worker）：轮询队列，取出任务在事件循环中执行；
- 任务状态：queued → running → complete/failed，结果存 Redis（带 TTL）。

### 3.3.2 关键 API 与坑

```python
# 入队（job_id 自定义 = thread_id，任务记录与队列任务天然对应）
job = await pool.enqueue_job("run_agent_task", query, thread_id, user_id, _job_id=thread_id)

# 取消（必须显式超时！）
await job.abort(timeout=2.0)  # 默认 timeout=None 会无限等待 worker 确认
```

**abort 的行为**：先把 job 从队列移除（或标记），然后等待任务结果确认。没有 worker 消费时，等待永远无法完成——HTTP 取消请求被挂死。

### 3.3.3 追问链

**Q：arq 的任务结果存哪里？**
A：Redis（key 带 TTL，默认 keep_result 3600 秒）。本项目的任务结果以 TaskStore（SQLite）为准，arq 结果仅作补充。

**Q：worker 崩溃了任务怎么办？**
A：arq 有 in-progress 集合：worker 崩溃后，重启时检测到 in-progress 中的任务会重新入队（abort 或重试，取决于配置）。本项目 max_tries=2（失败重试一次）。

**Q：任务重试会不会重复执行副作用？**
A：会——所以 run_agent_task 设计为幂等友好：任务状态以 TaskStore 为准（覆盖写），事件是 append-only（seq 单调递增不会重复），产物文件按 session_id 覆盖。重试不会产生脏数据。

## 3.4 JWT 认证

### 3.4.1 原理

JWT = Base64(Header).Base64(Payload).Signature

- Header：算法（HS256）；
- Payload：声明（sub=用户ID、exp=过期时间）；
- Signature：HMAC-SHA256(header.payload, secret)。

服务端验签即可信任 Payload（无需查库），但**用户是否存在仍需查库**（防止用户删号后旧 token 仍有效）。

### 3.4.2 本项目的取舍

- 密钥从环境变量读，默认值是开发用的（启动时打警告）；
- 有效期默认 24 小时（JWT_EXPIRE_MINUTES 可调）；
- 无 refresh token（用户量小，过期重登录可接受）；
- query 参数传 token（下载/WS）的固有风险：token 会进浏览器历史和日志——缓解是短有效期。

### 3.4.3 追问链

**Q：JWT 能撤销吗？**
A：无状态 JWT 本身不能（过期前一直有效）。撤销需要服务端黑名单（Redis 存 revoked token）或换短效 token + refresh 机制。本项目用“校验时查用户存在”做弱撤销（删号即失效）。

**Q：HS256 和 RS256 的区别？**
A：HS256 对称加密（签发验证同一密钥，适合单体服务）；RS256 非对称（私钥签发、公钥验证，适合微服务/第三方验证）。本项目单体服务，HS256 够用。

**Q：token 存 localStorage 安全吗？**
A：有 XSS 风险（JS 可读取）。更安全是 httpOnly Cookie（但 CSRF 防护复杂）。本项目是内部工具，XSS 面小（无用户生成 HTML 渲染），localStorage + 严格 CSP 是合理取舍。

## 3.5 FAISS 向量检索

### 3.5.1 原理

FAISS 把向量存为连续内存数组，检索时计算查询向量与库内向量的距离：

- IndexFlatL2：暴力计算 L2（欧氏）距离，精确但 O(n)；
- IVF 等索引：聚类分桶，近似检索，O(√n) 但有精度损失。

本项目用 IndexFlatL2（百万级以下精确检索完全够用）。

### 3.5.2 序列化与坑

```python
# 错误做法（C++ 层文件 IO，中文路径失败）
faiss.write_index(index, "中文路径/index.faiss")  # could not open for writing

# 正确做法（Python 层字节 IO）
raw = faiss.serialize_index(index)  # numpy uint8 数组
path.write_bytes(raw.tobytes())
index = faiss.deserialize_index(np.frombuffer(path.read_bytes(), dtype=np.uint8))
```

### 3.5.3 追问链

**Q：L2 距离和余弦相似度的区别？**
A：L2 是欧氏距离（受向量模长影响）；余弦是方向相似（归一化后）。OpenAI/百炼的 embedding 通常已归一化，两者等价。FAISS 的 IndexFlatIP 是内积（等价于归一化后的余弦）。

**Q：分片策略怎么定的？**
A：500 字符、重叠 80。依据：中文研报段落通常 200-800 字符，500 能覆盖一个完整论点；重叠 80 防止论点被切断。分隔符优先级：段落 → 换行 → 句号 → 分号 → 逗号（RecursiveCharacterTextSplitter）。

**Q：百万级向量怎么办？**
A：换 IVF 索引（faiss.index_factory(dim, "IVF4096,Flat"）或专用向量数据库（Milvus/Qdrant）。本项目数据量（几十个 PDF）远未触及，FAISS 单文件部署简单是首要考虑。

## 3.6 Prometheus 指标

### 3.6.1 原理

Prometheus 拉模式：定期（默认 15s）抓取 `/metrics` 端点，存时序数据库。四种指标类型：

- Counter：只增不减（请求数）；
- Gauge：可增可减（活跃任务数）；
- Histogram：分布（耗时，分桶统计）；
- Summary：分布（分位数，客户端计算）。

### 3.6.2 本项目的指标设计

| 指标 | 类型 | 标签设计 |
| --- | --- | --- |
| tasks_total | Counter | status（四个终态） |
| tasks_active | Gauge | 无 |
| tool_calls_total | Counter | tool（工具名） |
| http_requests_total | Counter | method/path/status |
| task_duration_seconds | Histogram | 无（分桶 1s~30min） |

**标签基数控制**：HTTP 指标的 path 用路由模板（`/api/task/{thread_id}`）而不是具体 ID——否则标签基数爆炸（每个 thread_id 一个时间序列）。

### 3.6.3 追问链

**Q：Counter 和 Gauge 的区别？**
A：Counter 单调递增（重启归零，用 rate() 算速率）；Gauge 瞬时值（直接读）。任务数用 Counter（算累计/速率），活跃数用 Gauge（看当前负载）。

**Q：Histogram 和 Summary 的区别？**
A：Histogram 在服务端分桶（可聚合多实例）；Summary 在客户端算分位数（准确但不可聚合）。多实例部署必须 Histogram。

**Q：多进程指标怎么聚合？**
A：每个进程暴露自己的 /metrics，Prometheus 分别抓取（加 instance 标签区分）。arq 模式下 worker 的指标（任务结局）在 worker 进程——需要 worker 也暴露端点或 Pushgateway。

## 3.7 LLM-as-judge 评测

### 3.7.1 原理

用强模型评审弱模型（或同模型自评）的输出。关键设计：

- **结构化输出**：强制 JSON（解析失败重试）；
- **temperature=0**：评审要确定性；
- **rubric 明确**：每个维度一句话定义 + 评判要求；
- **只依据给定材料**：防止评审引入外部知识。

### 3.7.2 本项目的三维设计

| 维度 | 评什么 | 为什么重要 |
| --- | --- | --- |
| correctness | 事实与数据是否准确 | 防编造（Agent 最大风险） |
| completeness | 是否完整回应任务各方面 | 防偷懒（只答一半） |
| groundedness | 结论是否有检索来源支撑 | 防幻觉（有据性） |

### 3.7.3 追问链

**Q：LLM 评审可靠吗？**
A：有主观性（temperature=0 缓解但无法消除）。缓解手段：明确的 rubric、只依据给定材料、宁严勿松的指令。工程上更可靠的是“确定性检查 + LLM 评审”组合——前者零成本每次跑，后者按需触发。

**Q：为什么不用人工评估？**
A：成本。22 个用例人工评一次要几小时，LLM 评审几分钟。人工评估用于校准（定期抽检 LLM 评审与人工的一致性），不是每次跑。

**Q：评审模型和被测模型一样会怎样？**
A：同模型自评有偏袒风险（模型偏爱自己的输出风格）。缓解：评审模型强于被测模型（如用 qwen-max 评 qwen-plus），或人工抽检校准。本项目默认评审模型与对话模型一致（成本考虑），生产建议换更强模型。
