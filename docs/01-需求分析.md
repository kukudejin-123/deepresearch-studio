# 01 需求分析

## 1.1 项目背景

### 1.1.1 行业背景

2025 年以来，大语言模型（LLM）应用开发的重心从“单次问答”转向“复杂任务自动化”。典型的复杂任务——行业研究、竞品分析、数据报告——具有三个共同特征：

1. **多源信息需求**：答案分散在互联网、内部数据库、私有文档、用户上传材料中，单一检索渠道无法覆盖；
2. **多步骤执行**：需要“规划 → 检索 → 验证 → 汇总 → 交付”的完整链路，单次模型调用无法完成；
3. **过程可观察**：用户需要知道系统在做什么、查到了什么、结论从何而来，而不是面对一个黑盒。

OpenAI 的 Deep Research 产品验证了这个方向，但闭源产品无法定制数据源、无法私有化部署。开源社区出现了两类方案：一类是研究框架（如 gpt-researcher，偏实验），一类是通用 Agent 平台（如 Dify，偏低代码），**缺少一个“用生产级工程手段实现深度研究场景”的完整参考实现**——这正是本项目的定位。

### 1.1.2 项目起源

本项目基于开源教学项目 [didilili/deepsearch-agents](https://github.com/didilili/deepsearch-agents)（DeepAgents 教程体系的实战项目）二次开发。原项目提供了完整的多智能体学习骨架：

- 一主三从的多智能体架构（主智能体 + 网络搜索/数据库/RAGFlow 三个专家助手）；
- FastAPI + WebSocket + React 的前后端闭环；
- 9 个真实工具（Tavily 搜索、MySQL 查询、RAGFlow 知识库、文件读写、Markdown/PDF 生成）。

但原项目明确声明了能力边界（README 原文）：**没有用户体系、没有任务队列、没有事件持久化、没有测试与 CI、依赖外部 RAGFlow 服务**。这些恰好是“从教学 demo 走向生产系统”必须补齐的能力。

因此本项目的需求可以概括为一句话：**在原有多智能体骨架基础上，补齐生产级工程能力，同时保持代码可读性与可学习性**。

### 1.1.3 目标用户

| 用户类型 | 使用场景 | 核心诉求 |
| --- | --- | --- |
| 学习者 | 系统学习 DeepAgents/LangGraph 工程开发 | 代码清晰、文档完整、能跑通 |
| 开发者 | 二次开发自己的多智能体应用 | 架构可扩展、接口清晰、可测试 |
| 求职者 | 作为简历项目展示工程能力 | 有深度、有亮点、经得起追问 |

## 1.2 核心场景

### 场景一：多源研究报告（旗舰场景）

**用户输入**：

> 结合公开资料、数据库信息和我上传的文档，整理一份机器人行业研究报告，并生成 PDF。

**系统行为**：

1. 主智能体分析任务，识别出需要三类信息源：公开网络、内部数据库、用户上传文件；
2. 调度网络搜索助手检索行业趋势与政策；
3. 调度数据库查询助手获取内部销售数据；
4. 通过文件工具读取用户上传的文档；
5. 汇总三类信息，判断资料是否充分（不充分则追加检索）；
6. 调用 Markdown 生成工具产出报告，再转换为 PDF；
7. 全过程通过 WebSocket 实时推送给前端，用户可随时取消。

**验收标准**：报告内容区分信息来源；生成的 PDF 可下载；执行过程可见；取消后状态正确。

### 场景二：结构化数据查询

**用户输入**：

> 从数据库中查询心血管药品的库存情况，并生成 Markdown 报告。

**系统行为**：主智能体调度数据库查询助手 → 助手先列出表名 → 预览表结构 → 执行 SQL → 返回 CSV 结果 → 主智能体汇总并生成报告。

**验收标准**：库存数字来自真实查询；报告文件生成成功；SQL 经过只读校验。

### 场景三：私有知识库问答

**用户输入**：

> 检索本地知识库中关于货币政策的研究结论。

**系统行为**：主智能体调度知识库助手 → 助手先列出可用集合 → 选择匹配集合 → 语义检索 → 返回带来源的文档分片 → 主智能体汇总。

**验收标准**：检索结果带来源文件名；结论可在知识库文档中找到依据；用户私有库与共享库隔离。

### 场景四：长任务与断线（工程场景）

**用户行为**：提交一个耗时数分钟的研究任务 → 关闭浏览器 → 重新打开 → 期望看到之前的执行过程。

**系统行为**：执行事件全量落库 → 前端重连后按 seq 增量回放 → 实时事件与回放事件去重。

**验收标准**：刷新页面不丢执行过程；事件不重复；任务最终状态正确。

### 场景五：多用户隔离（安全场景）

**用户行为**：用户 A 提交任务并生成文件 → 用户 B 尝试访问 A 的任务和文件。

**系统行为**：所有资源接口校验归属 → 越权访问返回 404（不暴露资源存在性）。

**验收标准**：B 无法查看/取消/下载 A 的任何资源；B 的任务列表只含自己的任务。

## 1.4 非功能需求

### 1.4.1 性能需求

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 接口响应时间 | P99 < 500ms | 不含 Agent 执行（任务异步化） |
| 事件推送延迟 | < 100ms | WebSocket 实时事件 |
| Embedding 缓存命中率 | > 60% | 重复检索场景 |
| 单用户并发上限 | 2 个任务 | 防止打爆 LLM 配额 |
| 任务提交频率 | 10 次/分钟 | 滑动窗口限流 |

### 1.4.2 安全需求

- 所有资源接口默认要求认证（AUTH_ENABLED=false 仅限开发调试）；
- 跨用户资源访问一律拒绝，且不暴露资源存在性（404 而非 403）；
- 模型生成的 SQL 必须经过工具层只读校验，不依赖提示词约束；
- 上传文件必须经过类型白名单、大小上限、文件名清洗；
- 密码必须哈希存储（PBKDF2-SHA256，10 万次迭代）；
- JWT 密钥必须可配置，生产环境禁止使用默认值。

### 1.4.3 可维护性需求

- 代码结构分层清晰（agent/api/tools/rag/queue/events/eval），模块间依赖单向；
- 核心机制有文档（docs/ 目录），关键决策有记录（ADR 风格）；
- 测试覆盖核心链路，重构有安全网；
- 日志结构化，可接入日志聚合系统。

### 1.4.4 可扩展性需求

- 任务队列可切换实现（memory → arq → 未来 Celery）；
- 检查点存储可切换（SQLite → PostgreSQL）；
- 新增专家助手只需实现字典式子智能体协议；
- 新增工具只需实现 LangChain @tool 接口。

## 1.5 需求边界（明确不做的）

| 不做的事 | 原因 |
| --- | --- |
| 角色权限细分（RBAC） | 当前“本人 or 拒绝”模型满足需求，RBAC 属过度设计 |
| 运行中任务断点续跑 | 取消即终止；检查点具备恢复条件但 resume 未实现 |
| 文件内容审核（病毒扫描） | 需要外部安全服务，超出项目范围 |
| 微服务拆分 | 单体 + 队列足够，拆分反而增加复杂度 |
| 自研向量数据库 | FAISS 满足百万级以下场景 |
| 前端框架重写 | React + Vite 现状够用，精力放在后端深度 |
