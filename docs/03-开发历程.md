# 03 开发历程

本文档完整记录三期工程化改造的动机、方案与踩坑过程。这是项目最有价值的部分——每个决策都有真实的问题驱动，每个坑都有排查过程。

## 3.1 起点：原版项目的状态

原项目（didilili/deepsearch-agents）提供了完整的多智能体学习骨架：

**已有的**：

- 一主三从架构（主智能体 + 网络搜索/数据库/RAGFlow 助手）；
- 9 个工具（Tavily、MySQL 三件套、RAGFlow 两件套、文件读取、Markdown、PDF）；
- FastAPI + WebSocket + React 前后端闭环；
- ContextVar 会话隔离、monitor 事件推送。

**原版 README 自己声明的能力边界**：

> 它没有刻意展开以下生产治理能力：用户登录、角色权限和多租户隔离；文件上传安全扫描；任务队列、分布式执行；全量事件持久化；系统化评测集；生产监控、告警、链路追踪。

这六条就是三期改造的需求清单。

## 3.2 第一期：安全与多用户基础

### 3.2.1 动机

原版最大的硬伤：**任何人只要知道 thread_id 就能读写别人的会话**。任务接口、文件接口、WebSocket 全部无认证。这在演示时无妨，但离“能给别人用”差得远。

### 3.2.2 实施内容

**用户体系**（app/api/auth.py）：

- SQLite 用户存储 + PBKDF2-SHA256 密码哈希（标准库实现，不引 bcrypt）；
- PyJWT 签发/校验，`get_current_user` FastAPI 依赖；
- 注册/登录/me 三个接口；前端登录注册页；
- `AUTH_ENABLED=false` 开发模式退路。

**资源隔离**：

- 任务表加 user_id 列（含旧库 ALTER TABLE 迁移）；
- 会话目录/上传目录/输出目录按 `user_{id}/` 分层；
- 任务查询/取消、文件列表/下载全部校验归属，跨用户一律 404；
- 知识库支持用户私有库 + 共享库分层。

**SQL 防护**（app/tools/sql_guard.py）：

- 只读校验（SELECT/SHOW/WITH/EXPLAIN 开头）；
- 关键字黑名单（词边界匹配，不误伤 updated_at）；
- 多语句拦截 + 注释绕过防护；
- 表名白名单。

**上传安全**（app/api/upload_guard.py）：

- 扩展名白名单、流式大小校验、文件名清洗。

**限流**（app/api/rate_limit.py）：

- 滑动窗口：任务按用户、登录按 IP+用户名。

### 3.2.3 踩坑记录

**坑 1：WebSocket 重复 accept**

现象：带 token 连接 WebSocket 时报 `RuntimeError: Expected ASGI message "websocket.send" or "websocket.close", but got 'websocket.accept'`。

排查：认证辅助函数里调了 `websocket.accept()`，随后 `manager.connect()` 又调了一次。WebSocket 协议只能 accept 一次。

修复：认证函数只校验不 accept，accept 统一由 ConnectionManager 执行。

**坑 2：隐藏文件绕过**

现象：测试 `.env` 文件应被拒绝，但 `sanitize_filename(".env")` 返回了 `"env"`（前导点被剥掉），后续的隐藏文件检查失效。

排查：`strip(".")` 会同时剥离首尾的点号。

修复：改为 `rstrip(".")`（只剥尾部），前导点保留供下一步拒绝。

**坑 3：越权访问返回 200**

现象：端到端测试发现用户 B 下载用户 A 的文件返回 HTTP 200 + 错误 JSON 体。

排查：原版文件接口用“200 + {error: ...}”表示拒绝，浏览器和监控都无法识别失败。

修复：改为正确的 403/404 状态码。

## 3.3 第二期：可靠执行与可观测性

### 3.3.1 动机

第一期解决了“谁能用什么”，第二期解决“执行可不可靠”：

- 任务在 API 进程内执行，服务重启后运行中任务丢失；
- WebSocket 断了执行过程就看不到了；
- 没有任何指标，任务失败只能翻日志。

### 3.3.2 实施内容

**任务队列抽象**（app/queue/）：

- TaskQueue 协议 + memory/arq 双实现；
- 独立 worker 进程（app/worker/tasks.py）；
- 提交接口队列化，入队失败返回 503 并标记 failed（不留僵尸任务）。

**事件持久化与桥**（app/events/）：

- EventStore：SQLite 落库（WAL 多进程并发写）；
- RedisEventBridge：Pub/Sub 跨进程转发；
- 事件回放接口 + 前端 seq 去重。

**协作式取消**：

- 取消接口置位状态，执行侧定期检查主动收尾。

**可观测性**（app/api/metrics.py）：

- Prometheus 四类指标 + 请求计数中间件。

**PostgreSQL 检查点分支**：

- 可选 extra，多 worker 共享会话状态。

### 3.3.3 踩坑记录（本期最密集）

**坑 4：同步检查点不支持异步图**

现象：换成 SqliteSaver 后，任务执行报错：

```
The SqliteSaver does not support async methods.
Consider using AsyncSqliteSaver instead.
```

排查：主智能体通过 `astream` 异步执行，LangGraph 只调用检查点的异步接口（aput/aget）。同步的 SqliteSaver 没有这些方法。

修复：改用 AsyncSqliteSaver（aiosqlite 驱动）；主智能体改为惰性异步组装（首次任务时创建，带并发锁）。

**坑 5：arq func() 装饰器误用**

现象：worker 启动失败：`TypeError: func() missing 1 required positional argument: 'coroutine'`。

排查：arq 的 `func` 第一个参数是位置参数，`@func(name=...)` 纯关键字装饰器写法不合法。

修复：显式构造 Function 对象：`functions = [func(run_agent_task, name=..., timeout=..., max_tries=...)]`。

**坑 6：Job.abort() 无限等待**

现象：arq 模式下取消接口永久挂起（测试脚本超时被杀）。

排查：arq 的 `Job.abort()` 内部 `await self.result(timeout=None)`——默认无限等待 worker 确认。没有 worker 消费时，取消请求被永久挂死。

修复：显式传超时 `job.abort(timeout=2.0)`。中止信号在等待前已写入 Redis，超时仅表示无人确认。

**坑 7：WebSocket 归属校验过严**

现象：端到端测试中，前端“先建 WebSocket 再提交任务”的正常流程被 403 拒绝。

排查：最初要求“任务必须存在且属于本人”，但前端 thread_id 由客户端预生成，连接时任务还没提交。

修复：改为“任务不存在时允许预订阅（thread_id 为 UUID 且按用户本地存储），任务属于他人时拒绝”。

**坑 8：Redis 订阅循环零订阅崩溃**

现象：arq 模式下事件完全不推送（但落库正常），API 日志里有一行异常后静默。

排查：API 启动时还没有 WebSocket 连接，订阅循环在“零订阅”状态下调用 `pubsub.get_message()`，redis-py 直接抛 `"pubsub connection not set"`，异常被 `except Exception` 吞掉后循环退出——桥接静默死亡。

修复：零订阅时跳过读取（`if not subscribed: await asyncio.sleep(0.5); continue`）。

**坑 9：进程不退出**

现象：冒烟测试脚本功能全对但不退出。

排查：arq 连接池的 redis 连接线程阻止进程退出。

修复：测试脚本显式 `await queue.close()`。

## 3.4 第三期：质量体系与部署交付

### 3.4.1 动机

前两期让系统“能跑、安全、可靠”，第三期解决“怎么证明它好”和“怎么交付”：

- 改了提示词/工具，怎么知道 Agent 变好还是变坏？
- 别人怎么一分钟跑起来？

### 3.4.2 实施内容

**评估体系**（app/eval/）：

- 22 用例评测集（六类任务）；
- 三层判定：确定性检查 + 链路检查 + LLM 评审；
- 结果存储 + 回归对比；
- CLI（run/compare/list，--mock 冒烟）。

**容器化**：

- 后端/前端多阶段 Dockerfile；
- compose 全家桶（api/worker/frontend/mysql/redis + postgres profile）；
- Nginx 同源反代。

**CI/CD**：

- docker.yml：镜像构建推送 GHCR；
- eval.yml：每周评测回归。

**性能优化**：

- Embedding LRU 缓存；
- MySQL 连接池；
- 单用户并发上限。

### 3.4.3 踩坑记录

**坑 10：评测工具匹配失效**

现象：所有用例的链路检查都失败（missing_tools 包含所有期望工具）。

排查：`expected.lower() not in {name.lower() for name in tool_names}` 是集合成员判断（要求完全相等），而工具名是“数据库表名查询工具：list_sql_tables”这样的长字符串，期望值“数据库”永远不相等。

修复：改为子串匹配 `any(expected.lower() in name for name in normalized_tools)`。

**坑 11：空权重导致分数恒 0**

现象：mock 评审全 0.8 分，但加权分算出 0.0。

排查：`compute_weighted_score(scores, {})` 中权重为空 → total=0 → 除法得 0。

修复：空权重时退化为三维算术平均。

**坑 12：Embedding 批量结果静默过滤**

现象：代码审查发现 `return [v for v in results if v is not None]` 在异常情况下会少返回向量。

排查：若某个文本的向量化失败（results 中有 None），过滤后返回的向量列表与输入文本错位——FAISS 会拿到错误的分片向量且极难排查。

修复：`_finalize()` 严格校验，任何缺失直接抛错。

**坑 13：同秒提交排序不稳定**

现象：测试中连续保存两次运行，列表顺序随机。

排查：`ORDER BY created_at DESC` 在同一秒内无法区分先后。

修复：补 `rowid DESC` 次级排序。

## 3.5 三期演进逻辑

```
第一期：安全      → 解决“谁能用什么”（认证/隔离/防护）
第二期：可靠      → 解决“执行可不可靠”（队列/持久化/可观测）
第三期：质量+交付 → 解决“怎么证明好 + 怎么交付”（评测/容器化/性能）
```

每期都建立在前一期基础上：没有第一期的用户隔离，第二期的多进程共享存储无从谈起；没有前两期的稳定执行，第三期的评测无法可靠运行。
