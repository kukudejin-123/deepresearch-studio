# 06 质量评估体系

## 6.1 为什么 Agent 需要专门的评估体系

传统软件测试断言“输出等于期望值”，但 Agent 的输出是自然语言——同一个正确回答有无数种表述。且 Agent 的行为依赖模型，**改了提示词、换了模型、调了工具，质量可能悄悄退化而没有任何报错**。

评估体系要回答三个问题：

1. **这个回答对不对**（正确性）；
2. **这个回答全不全**（完整性）；
3. **这个结论有没有依据**（有据性，防编造）。

## 6.2 三层判定架构

```
┌────────────────────────────────────────────────────────┐
│ 第一层：确定性检查（零成本，每次 CI 可跑）                │
│  · must_include：答案必须包含的关键信息                   │
│  · must_not_include：答案不得包含的禁用语                 │
├────────────────────────────────────────────────────────┤
│ 第二层：执行链路检查（零成本）                            │
│  · expected_events：期望的事件类型是否出现                 │
│  · expected_tools：期望的工具是否全部被调用（子串匹配）     │
├────────────────────────────────────────────────────────┤
│ 第三层：LLM 评审（一次模型调用）                          │
│  · correctness / completeness / groundedness 三维打分     │
│  · 按用例权重加权，低于阈值判失败                          │
└────────────────────────────────────────────────────────┘
```

**通过条件**：三层全部通过（评审失败也判不通过，但确定性结果仍然记录）。

## 6.3 评测集设计

### 6.3.1 用例结构

```yaml
- id: db-001
  category: database_query
  query: 查询阿莫西林胶囊在各仓库的库存数量，并列出仓库位置。
  must_include: ["阿莫西林"]
  expected_events: [assistant_call, tool_start]
  expected_tools: ["数据库"]
  rubric_hints: 库存数字应来自数据库查询结果，仓库位置需与库中记录一致。
```

### 6.3.2 六类任务覆盖

| 分类 | 用例数 | 考察点 |
| --- | --- | --- |
| network_search | 4 | 检索是否发生、结果是否相关 |
| database_query | 5 | SQL 链路是否走到、数据是否准确 |
| knowledge_base | 4 | 集合发现与检索、来源标注 |
| file_reading | 3 | 上传文件解析（seed_files 预置） |
| multi_source | 3 | 多工具全部命中（网络+数据库+知识库） |
| file_generation | 3 | 检索→生成链路、文件真的生成 |

### 6.3.3 期望值的设计原则

- **must_include 用真实数据锚点**：如“阿莫西林”“芬必得”（MySQL 种子数据中的真实药品名），防止模型泛泛而谈蒙混过关；
- **expected_tools 用子串匹配**：写“数据库”可匹配“数据库表名查询工具：list_sql_tables”，用例不依赖具体工具改名；
- **多源用例要求全部命中**：multi-003 要求网络搜索、数据库、知识库三个工具都出现，防止模型只走一条链路。

## 6.4 LLM 评审设计

### 6.4.1 评审提示词

```
你是一个严格的 AI Agent 输出评审专家。
根据给定的任务、Agent 回答和执行过程，按三个维度打分（0~1 的一位小数）：

- correctness: 事实与数据是否准确，有无编造；
- completeness: 是否完整回应了任务的每个方面；
- groundedness: 关键结论是否有检索来源（工具调用结果）支撑。

评判要求：
1. 只依据给定材料评判，不引入外部知识；
2. 回答中的工具调用过程可用于判断 groundedness；
3. 宁严勿松：编造事实、答非所问应给低分。

只输出 JSON：{"correctness": 0.0, "completeness": 0.0, "groundedness": 0.0, "reasoning": "..."}
```

### 6.4.2 结构化解析

```python

    # 2. 定位第一个 { 到最后一个 }（容忍前后杂质文本）
    # 3. JSON 解析 + 维度校验（存在性、数值类型、0~1 范围）
```

**容错设计**：模型可能输出“```json {...} ```”或前后多说几句话，解析器都能处理；解析失败时首次重试一次（追加纠正消息），仍失败则记录 judge_error。

### 6.4.3 加权评分

```python
def compute_weighted_score(scores, weights):
    effective = weights or {"correctness": 1, "completeness": 1, "groundedness": 1}
    total = sum(effective.values()) or 1.0
    return round(sum(scores[d] * w for d, w in effective.items()) / total, 3)
```

用例可自定义维度权重（如文件生成类更看重完整性）；空权重退化为算术平均（修复过的坑 11）。

## 6.6 结果存储与回归对比

### 6.6.1 表结构

```sql
CREATE TABLE eval_runs (
    run_id TEXT PRIMARY KEY,
    dataset_path TEXT, judge_model TEXT,
    total INTEGER, passed INTEGER, avg_score REAL,
    created_at TEXT
);

CREATE TABLE eval_results (
    run_id TEXT, case_id TEXT, category TEXT,
    passed INTEGER, weighted_score REAL,
    deterministic_passed INTEGER, event_check_passed INTEGER,
    scores TEXT, answer_excerpt TEXT, failure_reason TEXT,
    UNIQUE (run_id, case_id)
);
```

### 6.6.2 回归判定

```python
for case_id, current_row in current.items():
    baseline_row = baseline.get(case_id)
    if baseline_row is None:
        continue  # 新用例不参与判定
    
    score_delta = current.score - baseline.score
    flipped_to_fail = baseline.passed and not current.passed
    
    if flipped_to_fail or score_delta <= -threshold:
        regressions.append(...)  # 回归
    elif score_delta >= threshold or (not baseline.passed and current.passed):
        improvements.append(...)  # 改善
```

**两种回归**：分数下降超阈值（质量退化）、由通过转失败（硬性回退，即使分数下降未超阈值）。

## 6.8 评估体系的局限与演进

**当前局限**：

- 22 个用例偏冒烟规模，覆盖广度优先于深度；
- LLM 评审有主观性（temperature=0 缓解但无法消除）；
- 评审维度固定三维，未覆盖“格式规范性”“响应延迟”等。

**演进方向**：

- 扩充用例到 50+，每类任务增加边界用例（信息不足、工具失败）；
- 引入多评审投票（同一用例跑 3 次取中位数）；
- 增加自动化指标（工具调用次数、token 消耗、端到端延迟）。
