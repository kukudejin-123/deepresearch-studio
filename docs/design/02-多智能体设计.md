# 02 多智能体设计

## 2.1 一主三从架构

### 2.1.1 架构图

```
                    用户任务
                       │
                       ▼
            ┌─────────────────────┐
            │     主智能体         │
            │  (Main Agent)       │
            │                     │
            │  · 任务理解与规划    │
            │  · 助手调度          │
            │  · 多源信息汇总      │
            │  · 文件交付          │
            └──────┬──────────────┘
                   │ task 工具调用
       ┌───────────┼───────────┐
       ▼           ▼           ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 网络搜索  │ │ 数据库   │ │ 知识库   │
│ 助手     │ │ 查询助手 │ │ 助手     │
│          │ │          │ │          │
│ Tavily   │ │ MySQL    │ │ FAISS    │
│ 搜索     │ │ 查询     │ │ 检索     │
└──────────┘ └──────────┘ └──────────┘
       │           │           │
       └───────────┴───────────┘
                   │ 结果返回
                   ▼
            ┌─────────────────────┐
            │   主智能体汇总       │
            │   + 文件工具交付     │
            │                     │
            │  read_file_content  │
            │  generate_markdown  │
            │  convert_md_to_pdf  │
            └─────────────────────┘
```

### 2.1.2 职责划分

| 角色 | 职责 | 工具 |
| --- | --- | --- |
| 主智能体 | 理解任务、规划步骤、决定调用哪个助手、汇总多源信息、生成交付物 | read_file_content、generate_markdown、convert_md_to_pdf |
| 网络搜索助手 | 检索互联网公开信息（新闻/政策/行业资料） | internet_search |
| 数据库查询助手 | 发现表、预览数据、执行只读 SQL | list_sql_tables、get_table_data、execute_sql_query |
| 知识库助手 | 发现集合、语义检索、返回带来源的分片 | list_knowledge_collections、search_knowledge_base |

### 2.1.3 为什么是一主三从

**为什么需要主智能体**：复杂任务需要“先想后做”——判断需要哪些信息源、分几步执行、信息是否充分。单智能体（一个模型 + 所有工具）在工具超过 5-6 个时选择准确率显著下降，且上下文会被所有工具的返回塞满。

**为什么是三个助手**：对应三类互不重叠的信息源（公开网络/结构化数据/私有文档）。每个助手的 system_prompt 可以针对其领域优化（如数据库助手强调“先列表再预览再查询”的步骤），工具数量控制在 1-3 个，模型选择准确。

**为什么不是更多**：每增加一个助手，主智能体的路由难度上升。三个是“覆盖主要信息源”与“路由可控”的平衡点。

## 2.2 子智能体协议

### 2.2.1 字典式子智能体

DeepAgents 支持两种子智能体声明方式：字典（dict）和 CompiledSubAgent（LangGraph 子图）。本项目使用字典式：

```python
network_search_agent = {
    "name": "网络搜索助手",                    # 主智能体路由时显示的名称
    "description": "负责进行网络知识搜索...",   # 主智能体判断是否调用的依据
    "system_prompt": "你是一个专业的网络信息查询助手...",  # 子智能体的行为约束
    "tools": [internet_search],                # 子智能体可调用的工具
}
```

### 2.2.2 description 的路由作用

主智能体根据每个助手的 `description` 决定是否调用。description 写得好坏直接决定路由准确率。本项目的 description 设计原则：

1. **明确职责边界**：“负责进行网络知识搜索...当需要从网络中查询数据的时候”；
2. **排除法**：“注意：在需要进行非内部信息，不是数据库数据和 RAGFlow 知识库数据的公开信息查询时，务必使用此助手”；
3. **举例**：知识库助手的 description 列举了“PDF、白皮书、研报、制度文件”等具体文档类型。

### 2.2.3 为什么不用 LangGraph 子图

CompiledSubAgent 适合需要复杂状态管理的子智能体（多轮对话、条件分支）。本项目的三个助手都是“单轮工具调用 + 结果返回”模式，字典式足够，且配置集中在 YAML 中便于调整。

## 2.3 提示词工程

### 2.3.1 提示词的组织

所有提示词集中在 `app/prompt/prompts.yml`，分两部分：

```yaml
main_agent:
  system_prompt: |
    你是金融与电商研究团队负责人...
    【关键执行顺序】
    1. 必须先调用子智能体获取信息
    2. 绝不允许在获取信息之前调用文件生成工具
    3. 严禁使用占位符内容生成文件
    4. 先搜索再生成，分两步进行

sub_agents:
  tavily:
    name: "网络搜索助手"
    description: ...
    system_prompt: ...
  db:
    ...
  knowledge_base:
    ...
```

### 2.3.2 主智能体提示词的关键约束

原版提示词中最有价值的四条约束（实践中验证有效）：

1. **执行顺序约束**：“必须先调用子智能体获取信息，绝不允许在获取信息之前调用文件生成工具”——防止模型跳过检索直接编造内容生成报告；
2. **禁止占位符**：“严禁使用'等待子任务完成'之类的占位符内容生成文件”——防止模型在子任务未完成时生成空壳报告；
3. **分步执行**：“如果你需要先搜索再生成，请分两步进行：第一步只调用搜索工具；第二步根据搜索结果调用生成工具。不要在一步（同一个 Tool Call 列表）中同时做这两件事”——防止并行调用导致的竞态；
4. **工作目录约束**：“新生成文件必须保存到工作目录...使用相对路径，禁止使用绝对路径”——配合 `resolve_write_path` 双重保险。

### 2.3.3 运行时动态提示词

除了静态 system_prompt，`run_deep_agent` 在每次任务开始时动态注入工作环境指令：

```
【工作环境指令】
工作目录: output/user_1/session_xxx
[已上传文件] 已加载到工作目录:
    - 报告.pdf
    请优先使用工具（read_file_content）读取并参考这些文件。

规则：
1. 新生成文件必须保存到工作目录
2. 读取已上传的文件时，请直接将文件名作为 filename 参数传入
3. 使用相对路径，禁止使用绝对路径
4. 若存在上传文件，请先分析内容
```

**为什么动态注入**：会话目录每次任务都不同（含 session_id），无法写在静态提示词里；上传文件列表也是运行时才知道。

## 2.4 工具设计

### 2.4.1 工具的实现模式

所有工具遵循同一模式：

```python
@tool
def tool_name(param: Annotated[str, "参数说明"]) -> str:
    """工具描述（模型据此决定是否调用）

    :param param: 参数说明
    :return: 返回值说明
    """
    monitor.report_tool(tool_name="...", args={...})  # 埋点
    # 业务逻辑
    return "结果字符串"
```

### 2.4.2 返回值设计

工具返回值统一为字符串（模型友好），分两类：

- **数据类**（SQL 查询、搜索）：返回结构化文本（CSV/JSON），模型可直接阅读；
- **状态类**（文件生成）：返回中文状态说明（“Markdown文件 'xxx' 已成功生成”），模型据此决定下一步。

### 2.4.3 错误处理

工具内部捕获异常并返回中文错误提示，**不向模型抛异常**——异常会中断整个 Agent 执行链，而错误提示让模型可以自我纠正（如换一个表名重试）。

### 2.4.4 工具安全

- SQL 工具：`sql_guard.py` 在工具层硬校验（只读 + 关键字黑名单 + 表名白名单）；
- 文件工具：`resolve_write_path` 强制收敛到会话目录；
- 搜索工具：Tavily 客户端惰性初始化，未配置密钥时返回提示而非崩溃。

## 2.5 上下文隔离

### 2.5.1 三级隔离

| 级别 | 机制 | 作用域 |
| --- | --- | --- |
| 会话级 | thread_id（LangGraph 检查点） | 同一会话的多轮对话共享上下文 |
| 任务级 | session_dir（文件系统目录） | 每个任务独立的工作目录 |
| 用户级 | user_id（目录分层 + 接口校验） | 不同用户的资源互不可见 |

### 2.5.2 ContextVar 的作用

深层工具（如 `generate_markdown`）需要知道当前会话目录，但工具签名不能传递这个参数（模型看不到）。解决方案：`ContextVar` 在协程级别存储上下文：

```python
# run_deep_agent 中设置
set_session_context(session_dir_str)
set_thread_context(session_id)
set_user_context(user_id)

# 工具中读取
session_dir = get_session_context()
```

**为什么是 ContextVar 而不是全局变量**：ContextVar 是协程隔离的，多个并发任务不会串台；全局变量在 asyncio 下会互相覆盖。

## 2.6 主智能体的组装

```python
main_agent = create_deep_agent(
    model=model,                              # OpenAI 兼容模型
    system_prompt=main_agent_content["system_prompt"],
    tools=[generate_markdown, convert_md_to_pdf, read_file_content],
    checkpointer=await get_checkpointer(),    # SQLite/PostgreSQL/内存
    subagents=[database_query_agent, network_search_agent, knowledge_base_agent],
)
```

**惰性异步组装**：`AsyncSqliteSaver` 需要在事件循环内创建，模块导入时没有 loop，因此推迟到首次任务执行时构建（带 asyncio.Lock 防并发重复构建）。
