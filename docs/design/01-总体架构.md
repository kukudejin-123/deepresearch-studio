## 1.2 进程模型

系统支持两种部署形态，通过 `TASK_QUEUE` 环境变量切换：

### 形态一：单进程（memory 模式，默认）

```
uvicorn app.api.server:app
```

- 所有组件在一个进程：API、任务执行（asyncio 后台协程）、WebSocket、事件存储；
- 事件不需要跨进程桥（monitor 直接推送到进程内 WebSocket 管理器）；
- 适合本地开发、演示、单用户使用；
- 重启后运行中任务丢失（状态已落库，可查询但不会自动恢复）。

### 形态二：多进程（arq 模式，生产）

```bash
uv run arq app.worker.tasks.WorkerSettings   # worker（可多开）
uv run uvicorn app.api.server:app            # API
```

- API 进程：接口、WebSocket、事件桥订阅端、队列客户端；
- Worker 进程：Agent 执行、事件发布端；
- 两者通过 Redis（队列 + Pub/Sub）和 SQLite/PostgreSQL（共享存储）协作；
- API 重启不丢已入队任务；worker 可水平扩展。

**关键设计**：两种形态共用全部业务代码，差异只在 `app/queue/` 的队列实现和 `app/events/bridge.py` 是否启用。

## 1.3 数据流

### 任务提交流程（arq 模式）

```
1. 前端 POST /api/task {query, thread_id}
2. API 认证 → 限流检查 → 并发上限检查
3. TaskStore.create(thread_id, query, user_id)  # 状态 running
4. ArqTaskQueue.submit() → Redis 入队（job_id = thread_id）
5. 返回 {status: started, thread_id, queue: arq}
6. Worker 消费任务 → run_deep_agent(query, thread_id, user_id)
7. 执行过程：monitor._emit() → EventStore.append()（落库）
                            → RedisBridge.publish()（跨进程）
8. API 进程事件桥订阅 → ConnectionManager.send_to_thread() → WebSocket
9. 任务结束：TaskStore.set_status(completed/failed/cancelled)
```

### 断线回放流程

```
1. WebSocket 断开（网络波动/刷新页面）
2. 前端 2 秒后自动重连（带 token query 参数）
3. 连接建立 → 前端调 GET /api/task/{id}/events?after_seq={lastSeq}
4. 服务端返回 seq > lastSeq 的事件列表
5. 前端合并到事件流（按 seq 去重）
6. 实时事件继续推送（seq 大于回放 max 的才会追加）
```

## 1.4 技术选型与决策记录

### 4.1 为什么用 DeepAgents 而不是裸 LangGraph

DeepAgents 封装了子智能体调度、文件系统后端、中间件机制，`create_deep_agent()` 一行完成组装。裸 LangGraph 需要手写子图路由、状态传递、工具分发，代码量翻倍且容易出错。**决策**：用 DeepAgents 做骨架，把精力放在工程化（安全/队列/评测）上。

### 4.2 为什么检查点用 SQLite 而不是 Redis

Redis 是内存数据库，重启后数据丢失（除非开 AOF 持久化，但查询能力弱）。SQLite 支持 SQL 查询（按 thread_id 检索、时间范围过滤），单文件部署简单。**决策**：默认 SQLite，生产多实例切 PostgreSQL。

### 4.3 为什么任务队列用 arq 而不是 Celery

Celery 是同步设计（worker 进程模型），在 FastAPI 异步生态中需要额外适配（事件循环冲突）。arq 原生 async，与 FastAPI/astream 完全兼容。**决策**：arq，且抽象出 TaskQueue 协议，未来可替换。

### 4.4 为什么事件桥用 Redis Pub/Sub 而不是消息队列

Pub/Sub 是“即发即忘”的广播，适合实时事件转发（丢了就丢了，因为事件已落库可回放）。消息队列（如 Redis Stream）有持久化和 ACK 语义，但增加复杂度。**决策**：Pub/Sub + SQLite 落库，实时性靠桥、可靠性靠库。

### 4.5 为什么 FAISS 而不是 Chroma/Milvus

FAISS 是纯计算库（无服务依赖），单文件索引，百万级以下性能足够。Chroma 需要额外服务进程，Milvus 是重量级分布式方案。**决策**：FAISS，且解决了中文路径写入问题（见踩坑复盘）。

### 4.6 为什么评测用 LLM-as-judge 而不是纯规则

Agent 输出的质量（完整性、有据性）无法用规则判断。纯规则只能做确定性检查（关键词命中）。**决策**：三层判定——确定性检查（零成本，每次 CI 跑）+ 链路检查（零成本）+ LLM 评审（按需触发）。

## 1.5 模块依赖关系

```
app/
├── agent/           # 智能体组装与执行（依赖 tools/api/context）
│   ├── main_agent.py
│   ├── checkpointer.py
│   └── subagents/
├── api/             # 接口层（依赖 agent/events/queue/auth）
│   ├── server.py
│   ├── auth.py
│   ├── monitor.py
│   ├── task_store.py
│   ├── rate_limit.py
│   ├── upload_guard.py
│   └── metrics.py
├── tools/           # 工具层（依赖 api/monitor、rag）
│   ├── tavily_tool.py
│   ├── db_tools.py
│   ├── vector_store_tools.py
│   ├── sql_guard.py
│   └── ...
├── rag/             # 向量库（依赖 embeddings）
├── events/          # 事件存储与桥（独立）
├── queue/           # 任务队列（依赖 agent/main_agent）
├── eval/            # 评测体系（依赖 agent/events/judge）
├── worker/          # arq worker 入口（依赖 agent/queue）
└── utils/           # 基础设施（日志/路径/转换）
```

**依赖原则**：上层可依赖下层，下层不依赖上层；`events/` 和 `utils/` 是最底层，不依赖任何业务模块。

## 1.6 配置体系

所有配置通过环境变量注入（`.env` 文件 + `python-dotenv` 加载），分五组：

| 组 | 变量 | 默认值 |
| --- | --- | --- |
| LLM | OPENAI_API_KEY / OPENAI_BASE_URL / LLM_QWEN_MAX | 必填 |
| Embedding | EMBEDDING_MODEL | text-embedding-v3 |
| 检索 | TAVILY_API_KEY | 必填 |
| 存储 | CHECKPOINTER_TYPE / CHECKPOINTER_DB / VECTOR_STORE_DIR / AUTH_DB / EVENT_DB | sqlite / app/data/ |
| 队列 | TASK_QUEUE / TASK_QUEUE_REDIS_URL | memory / redis://127.0.0.1:6379/0 |
| 安全 | AUTH_ENABLED / JWT_SECRET / JWT_EXPIRE_MINUTES | true / 必填 / 1440 |
| 限流 | TASK_RATE_LIMIT / LOGIN_RATE_LIMIT / MAX_CONCURRENT_TASKS_PER_USER | 10 / 5 / 2 |
| 性能 | MYSQL_POOL_SIZE / EMBEDDING_CACHE_SIZE | 4 / 1024 |

**设计原则**：所有配置都有合理默认值（除密钥外），本地开发零配置可跑（AUTH_ENABLED=false + memory 队列）。
